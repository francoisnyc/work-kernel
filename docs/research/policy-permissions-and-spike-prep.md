# Keep policy in Postgres, gate agent egress

Build permissions as a **tree of scopes plus a separate set of explicit, audited grants**, keep all of it in the kernel's own Postgres, and evaluate it in-process in Go through one `Authorize` / `VisibleScopes` / `Project` API that every path calls: UI, API, search, exports, notifications, webhooks, agents and Temporal payloads. The research supports the narrow-only inheritance rule but rejects the idea that the kernel can ship without a widening primitive. Every serious product (Google Drive, Linear Enterprise, Jira Service Management, Notion, Dataverse) ships per-item grants or links, because helpdesks need request participants and docs need publishing. Banning widening just pushes users into copying items or creating oversized containers. Zanzibar-style services (SpiceDB, OpenFGA, Permify) are the wrong default here. The kernel's model is a tree, not a general graph, and an external authorization store brings a dual-write problem that Google and Canva still repair with periodic full syncs. Agents should be first-class principals with a human sponsor, acting either on behalf of a user (effective rights = user ∩ agent grant) or under their own admin-granted identity. Per-transition autonomy alone will not stop the 2024–2026 incident pattern: an agent reads attacker-written content, then leaks data through an outbound channel. The kernel must also gate egress and treat customer-written fields as untrusted. On the runtime side, a Temporal ticket workflow costs roughly **32 Actions, about $1.4K per million tickets on Business tiers plus about $1K of Active storage**: a quarter of a cent per ticket. That is cheap enough not to drive the decision, but storage is a bigger share than Temporal's guidance suggests. The outbox handoff should be a per-Item, sequence-ordered relay using Update-With-Start with a deterministic Update ID and a workflow-side watermark. The spike must measure real Action counts, history bytes, handoff latency and the failure cases, because several of the key numbers here are estimates rather than published figures.

## Work tools put defaults on the container, then bolt widening grants on the side

Nearly every product sets permission defaults on a container and adds a narrowing layer on the child. Confluence is the closest match to the kernel's rule. **View restrictions cascade to child pages, and space permission is a hard ceiling**: "Restrictions don't override a person's space permission" ([Confluence](https://confluence.atlassian.com/doc/page-restrictions-139414.html)). Notion goes the other way. When a user has access through several paths, **the broadest grant wins**, so a workspace-wide "Full access" overrides a page-level "Can view" ([Notion](https://www.notion.com/help/sharing-and-permissions)). Zendesk is similar: across end-user and organization settings, "the more permissive setting wins" ([Zendesk](https://support.zendesk.com/hc/en-us/articles/4408893451290-What-is-the-difference-between-ticket-access-at-the-organization-level-and-end-user-level)). Linear's private teams hide issues from non-members, and a private parent can only have private sub-teams, which is a narrow-only rule. But "permission settings are not inherited from parent teams by sub-teams," and a project can span public and private teams, with visibility computed per issue ([Linear](https://linear.app/docs/private-teams.md); [Linear roles](https://linear.app/docs/members-roles.md)).

Widening single items is a common, shipped feature, not an edge case. Notion has "Anyone on the web with link," expiring links and Publish, all of which Enterprise owners can turn off ([Notion](https://www.notion.com/help/sharing-and-permissions)). Linear Enterprise lets team owners allow sharing individual private-team issues with non-members. Recipients can edit most details but **cannot see team, project, cycle or milestone, and cannot reshare** ([Linear](https://linear.app/docs/private-teams.md)). Google Drive went single-parent in 2020, replacing multi-homing with shortcuts. In that same change it kept explicit grants that live alongside inheritance: when an item moves, "**inherited access is lost, but directly added access is kept**" ([Google Workspace](https://workspace.google.com/blog/product-announcements/simplifying-google-drives-folder-structure-and-sharing-models)). Drive is the strongest precedent for the kernel. It validates single-container, and it shows that single-container works only alongside a grant layer. Jira Service Management shows what happens without one. Request participants **lose portal access once an issue security level is set**, the participants field cannot be added to a level, and admins fall back on Automation that copies participants into a custom field ([Atlassian KB](https://support.atlassian.com/jira/kb/set-up-issue-security-for-request-participants-using-automation/)). A helpdesk built on a strict narrow-only kernel would hit exactly this wall.

| Product | Container default | Child narrowing | Child widening | Combining rule |
|---|---|---|---|---|
| Confluence | Space permission (ceiling) | View restrictions cascade; edit restrictions per page | None beyond space | Intersection; space is a hard cap |
| Notion | Workspace / teamspace | Subpage restriction | Web link, Publish, guests | Broadest grant wins |
| Linear | Team (public/private) | Private sub-teams | Enterprise per-issue sharing | Membership; no sub-team inheritance |
| Jira / JSM | Project permission scheme | Issue security level | Participants (fights security levels) | Scheme + level; workarounds |
| Zendesk | Org / end-user access | — | Org-wide access | Most permissive wins |
| Google Drive | Folder | — | Direct grants survive moves | Inherited ∪ direct |

Field-level security splits the market. Salesforce, Dataverse and ServiceNow ship it as a layer evaluated after record access. Salesforce applies field permissions "across the app, including related lists, list views, reports and search results" ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/data_security/data_security_fields)). ServiceNow evaluates table ACLs first and field ACLs second ([ServiceNow Community](https://www.servicenow.com/community/platform-privacy-security/access-control-when-users-can-t-see-what-they-should/ta-p/3571378)). Jira refused. **JRA-1330, opened in 2003, was closed Won't Fix**, citing an estimated 12–18+ months of rewrite, admin bloat and performance risk ([JRA-1330](https://jira.atlassian.com/browse/JRA-1330)). The lesson is that field security has to live in the read path from day one, because retrofitting it means touching every outbound surface. Two usability details are worth copying. Dataverse returns secured columns as null so "the caller can't tell a secured value from a null value", and that ambiguity confuses users ([Microsoft Learn](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/column-level-security)). Return an explicit redaction marker instead. Dataverse also supports per-record field sharing, an early sign that "Finance only" fields eventually need exceptions such as "employees see their own salary."

External users fall into three models. Guest seats inside the host tenant (Slack, Linear, Notion) are limited to explicitly granted containers and often billed like members. Slack multi-channel guests are billed as members, and single-channel guests are free up to five per paid member ([Slack](https://slack.com/help/articles/202518103)). Federated sharing is the second model (Slack Connect). Non-seat customers are the third (Zendesk end users, JSM customers), who see their own or their organization's tickets through a portal. Guests typically cannot browse the directory, mention user groups or install apps, and their access can expire. Linear warns twice that "**enabled integrations may expose data beyond their teams**" ([Linear roles](https://linear.app/docs/members-roles.md)). Slack guests also see full channel history. That is fine for chat, but on a helpdesk Item it means internal notes need their own narrower visibility, not just container scope.

## Moves and secondary read paths cause most of the real leaks

Moves are where inheritance models break. In **Jira JRACLOUD-74636**, moving an issue with a security level into a project with a different scheme made it disappear: Jira never checked whether the level existed at the destination, the move succeeded, and nothing was logged ([JRACLOUD-74636](https://jira.atlassian.com/browse/JRACLOUD-74636)). The reverse bug, **JRACLOUD-99207 (August 2026)**, silently carried a security level over to a type with no security scheme ([JRACLOUD-99207](https://jira.atlassian.com/browse/JRACLOUD-99207)). Notion re-permissions only the moved page: "Subpage permissions stay the same" ([Notion](https://www.notion.com/help/sharing-and-permissions)). Confluence strips inherited restrictions from children when a parent becomes a blog post ([Confluence](https://confluence.atlassian.com/doc/page-restrictions-139414.html)). GitHub takes the conservative line: "**A private repository issue cannot be transferred to a public repository**," and users who lose access see a banner, not the content ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository)). The kernel should copy GitHub. A move that widens the effective read set is blocked or needs explicit confirmation, and a move that would orphan a narrowing policy is rejected outright instead of silently degrading.

The second leak channel is every read path that isn't the main UI. Linear documents that personal API keys, team webhooks, Airbyte syncs and workspace exports can all surface private-team data ([Linear](https://linear.app/docs/private-teams.md)). In 2019, default "Everyone" visibility on Jira filters and dashboards exposed staff directories and secret project names at NASA, Google and UN bodies ([SecurityWeek](https://www.securityweek.com/jira-misconfiguration-leaks-data-fortune-500-companies/)). GitLab has a long series of confidential-issue disclosure CVEs, for example [CVE-2024-3976](https://www.wiz.io/vulnerability-database/cve/cve-2024-3976) and [CVE-2026-1732](https://www.sentinelone.com/vulnerability-database/cve-2026-1732/). The research did not establish which path each CVE used. Microsoft's advisory CW1226324 described Copilot Chat summarizing confidential-labeled email despite DLP because a code path for Sent Items and Drafts ignored the label. This comes from a second-hand summary marked as a draft ([Bastion](https://www.bastion.tech/blog/microsoft-copilot-dlp-bypass-oversharing-guide)). The common thread is clear even where details are thin: **rules declared once leak through whichever egress path forgot to call them**. The kernel's list of such paths is long. It includes search snippets and facets, exports, notification templates, webhooks, outbox payloads, event-log readers, AI context assembly and Temporal workflow history, which persists activity inputs and is effectively a shadow copy of Item data.

Accumulated widening grants become a liability at AI scale. In a July 2026 CoreView survey, **two-thirds of organizations had delayed or cancelled Copilot rollouts, and 73% of those feared AI would surface confidential data**. The CEO blamed "a decade of sharing links and permissions nobody cleaned up" ([Infosecurity Magazine](https://infosecurity-magazine.com/news/microsoft-copilot-delayed-over)). Public and guest access is the worst case. Misconfigured Salesforce Community guest access leaked SSNs and loan documents for the State of Vermont and others in 2023 ([KrebsOnSecurity](https://krebsonsecurity.com/2023/04/many-public-salesforce-sites-are-leaking-private-data/)). Grants must therefore be visible, bounded, expiring where possible, and covered by access reviews. They should not be invisible exceptions.

## Keep authorization data in Postgres and evaluate it in Go

No engine answers "which items can this user see, sorted, paginated and full-text searched" well at scale without a precomputed permission index near the data or a search-then-check loop. OpenFGA's ListObjects defaults to **1,000 results and a 3 s deadline**, and its own docs recommend filtering in your database and then calling BatchCheck for large sets ([OpenFGA](https://openfga.dev/docs/interacting/relationship-queries)). AuthZed sells Materialize as the escalation path "once LookupResources reaches its performance ceiling," pushing precomputed permission sets into your own database so authorization becomes a JOIN ([AuthZed](https://authzed.com/products/authzed-materialize)). Calendly runs SpiceDB on Postgres with **Check p95 under 40 ms**, the only production latency figure the research found. Calendly deliberately avoided "listing every resource a user can access at scale" and hit a SERIALIZABLE retry incident inside SpiceDB's datastore ([Calendly](https://calendly.com/blog/how-calendly-standardized-authorization-with-spicedb)). The kernel already has the precomputed index those vendors sell: one `scope_id` per Item and a per-principal set of visible scopes.

The decisive argument is consistency. With an external authorization store, permission writes and content writes are a dual write. Google and Canva's experience is that an outbox gives at-least-once delivery but does not fix races. Google saw **tens to hundreds of discrepancies per day** and ran full sync jobs several times daily ([AuthZed / Canva](https://authzed.com/blog/the-dual-write-problem-in-spicedb-a-deep-dive-from-google-and-canva-experience)). Rover replaced OpenFGA with a recursive SQL function over a view in about a weekend. Its reasons were tuples for every entity, cross-system rollbacks, GDPR deletes reimplemented outside the database, and manual edits bypassing sync ([Rover](https://getrover.substack.com/p/how-we-rewrote-openfga-in-pure-postgres)). If grants, groups and the scope tree commit in the same transaction as content, the new-enemy problem (a revoked user sees content added after the revocation because of a stale allow) disappears by construction.

| Option | Strength for this kernel | Weakness for this kernel | Verdict |
|---|---|---|---|
| **In-process Go over Postgres tables** | Transactional with content; the tree fits a scope table; one API for all paths | You build the explainer, tests and tooling (Figma did) | **Core choice** |
| Cedar (cedar-go) | ABAC conditions, `forbid` for narrowing, analyzable | cedar-go lacks a production validator, templates and core partial evaluation; `x/exp` is not semver-stable ([pkg.go.dev](https://pkg.go.dev/github.com/cedar-policy/cedar-go)); Rust `tpe` is experimental ([docs.rs](https://docs.rs/cedar-policy)) | Optional rule language for field/transition conditions; not the scope core |
| Amazon Verified Permissions | Managed Cedar | **200 RPS IsAuthorized default** per store, network hop ([AWS](https://docs.aws.amazon.com/verifiedpermissions/latest/userguide/quotas.html)) | Unsuitable for per-row checks |
| OPA / Rego | Most mature policy-to-SQL compile path; Apache-2.0, CNCF Graduated ([OPA](https://www.openpolicyagent.org/docs/filtering/partial-evaluation)) | Steep language; compile fragment restrictions | Only if the team accepts Rego |
| SpiceDB / OpenFGA / Permify | Deep ReBAC graphs; consistency tokens | Second source of truth; dual write; weak list APIs | Reject as default |
| Oso Cloud | `list_local` returns a SQL WHERE clause | Proprietary SaaS; Go support for `list_local` unconfirmed ([Oso](https://www.osohq.com/docs/develop/enforce/list-filtering)) | Not needed |
| Postgres RLS | Defense in depth | Leakproof and subplan planning traps; hard to test, debug or explain ([Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-limitations-and-alternatives/)) | Tenant fence only |

The recommendation follows Figma's path more than any vendor's. Figma evaluated OPA, Zanzibar and Oso and found that "none really got to the core of what we were trying to solve." It built a JSON-serializable, IAM-like DSL with three-valued evaluation, which cut evaluation time by more than half. Its React debugger shows each node's evaluated data, and a shared cross-language test suite keeps implementations aligned ([Figma](https://www.figma.com/blog/how-we-rolled-out-our-own-permissions-dsl-at-figma/)). Vanta's lesson after adopting Oso points the same way: the platform around the engine is the real work, and declarative policy lets you generate permission matrices and catch drift ([Vanta](https://www.vanta.com/resources/how-we-built-authorization-as-a-platform-lessons-from-scaling-fine-grained-access-controls-at-vanta)). Concretely, keep the scope tree, grants, groups and Type field rules as data in Postgres. Evaluate them with a small, typed Go evaluator. Express Type-level conditions in a declarative rule format that can be tested and diffed in CI. Add cedar-go's core evaluator for those conditions only if its maturity is acceptable when you build it. Add an RLS `tenant_id` fence as a backstop. Licensing was not verified for every engine (the notes confirm Apache-2.0 only for OPA), and no source gave p50/p99 latency for Cedar, OPA, OpenFGA, Oso or Permify.

## Agents need their own principal, an intersection rule, and egress gates

Vendors have converged on two agent modes, and most support both. Microsoft Entra Agent ID separates **autonomous agents** using their own identity from **interactive agents** acting "on behalf of a signed-in user" through delegated permissions. Each agent has a **sponsor** who carries business accountability. Microsoft contrasts this with plain service principals, which have "no enforced sponsorship, no agent-aware audit entries" ([Entra](https://learn.microsoft.com/entra/agent-id/key-concepts)). Google Cloud gives each agent a SPIFFE principal, and when it acts for a user, audit logs show both identities. Google also warns that deleting an agent does **not** remove the IAM bindings that reference it ([Google Cloud](https://docs.cloud.google.com/iam/docs/agent-identity-overview)). Atlassian Rovo lets builders choose "user's account" (writes appear as the user) or "agent's account" (writes credited to the agent, permissions set by admins). It recommends the agent account for automation "to minimize security risks" ([Atlassian](https://support.atlassian.com/studio/docs/understand-rovo-agent-accounts/)). Strict user ∩ agent intersection is not a shipped default. Atlassian users are filing requests for "intersecting permissions with invoking user" ([ROVO-837](https://jira.atlassian.com/browse/ROVO-837)). The IETF draft that would carry user → agent delegation chains in tokens has **expired** ([IETF](https://datatracker.ietf.org/doc/draft-oauth-ai-agents-on-behalf-of-user/)). The kernel should enforce intersection itself instead of waiting for a standard.

MCP covers the transport layer, not agent identity. The current **2026-07-28 spec** treats servers as OAuth resource servers with audience-bound tokens, prefers Client ID Metadata Documents over deprecated Dynamic Client Registration, binds client credentials to the issuer, and removes sessions in favor of stateless requests ([MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Clients must use Resource Indicators so that "a token minted for Server A can't be replayed against Server B" ([WorkOS](https://workos.com/blog/mcp-2026-spec-agent-authentication)). The spec does not model "agent X on behalf of user Y". That comes from the identity provider (Entra Agent OBO, Google 3LO) and must be mapped into the kernel's own principal model at the MCP server boundary.

The incident record is consistent, and it changes what "safe" means. **Slack AI (August 2024)**: an injected instruction in an attacker's public channel made Slack AI render a "reauthenticate" link carrying the victim's private API key. The citation pointed only at the victim's message, and Slack first called it "intended behavior" ([PromptArmor](https://promptarmor.substack.com/p/data-exfiltration-from-slack-ai-via)). **GitHub MCP (May 2025)**: a malicious public issue made an agent holding the user's token leak private-repo data into a public PR ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). **Supabase/Cursor (July 2025)**: a support ticket instructed an agent running with `service_role` (which bypasses RLS) to read `integration_tokens` and post them back into the ticket ([Simon Willison](https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta)). **ForcedLeak (September 2025, CVSS 9.4)**: instructions in an external Web-to-Lead field made Agentforce render lead emails into an image URL on an allowlisted domain that had expired and that researchers bought for $5 ([The Register](https://www.theregister.com/2025/09/26/salesforce_agentforce_forceleak_attack/)). **GitLost (July 2026)**: a public issue made GitHub Agentic Workflows post a private README, bypassing threat detection with the prefix "Additionally," ([The Hacker News](https://thehackernews.com/2026/07/public-github-issue-could-trick-github.html)). **Atlassian Rovo (2026)**: two exfiltration disclosures, one unresolved at publication, where disabling web search did not remove the URL-opening capability ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-atlassian-rovo-prompt-injection-data-exfil/)). Separately, Asana's MCP server had a plain **cross-tenant bug** and went offline June 5–17, 2025 ([The Register](https://theregister.com/2025/06/18/asana_mcp_server_bug/)). Simon Willison's "lethal trifecta" names the shared structure: private data, exposure to untrusted instructions, and a way to send data out ([Simon Willison](https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta)).

Two conclusions follow. First, **in almost every case the agent stayed within a legitimate principal's rights**, or ran with a service role. So "agent acts as the user" is the precondition for the attack, not a defense. Second, these were reads followed by egress, so approval gates on state transitions would not have caught them. The guardrails that work in production are separation of duties and attribution. GitHub "prevents the user who asked Copilot cloud agent to create a pull request from approving it," requires workflow approval on agent PRs, filters hidden characters, firewalls the agent's network, and authors commits as Copilot with the human as co-author and a link to the session log ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). Salesforce reserves `Send Email` for humans so the agent can only draft, according to a single secondary source ([SalesforceBreak](https://salesforcebreak.com/2026/10/08/admin-permissions-agentforce/)). The counter-evidence is fair to state: most incidents were researcher proofs of concept with no confirmed exploitation, and vendors fixed them quickly with egress allowlists and read-only defaults. The risk is manageable with defense in depth. It is not manageable with authentication alone. No vendor documentation was found for per-agent spend budgets or rate limits in work tools, though the research did not search for them specifically.

## Compliance pushes personal data out of the append-only log

Auditors expect periodic, documented access reviews. SOC 2 sets no frequency, but quarterly with a named reviewer is the practical norm. ISO 27001:2022 expects privileged access reviewed at least every six months, leavers revoked the same day, and **an inventory of non-human identities with named human owners** ([Iden](https://www.idenhq.com/blog/identity-evidence-playbook-iso-27001-soc-2)). Non-human identities are "the blind spot in most identity programs," and privileged-activity logs should be "stored where the privileged user cannot edit them." Agents with sponsors, an entitlement report per principal, and recertification events in history map directly onto SOC 2 CC6.1–CC6.3 and ISO A.5.15–A.5.18. Neither framework fixes an audit-log retention period. That has to come from contracts or sector rules.

Regulators reject immutability as an excuse. The Berlin DPA fined Deutsche Wohnen **€14.5M in 2019** partly because its archive could not delete data, and said it should have used a system that separates data by retention period ([Data Protection Report](https://www.dataprotectionreport.com/2019/11/first-multi-million-gdpr-fine-in-germany-e14-5-million-for-not-having-a-proper-data-retention-schedule-in-place/)). The fine was later litigated, and the final outcome was not verified. The EDPB's 2025 blockchain guidelines say identifiable data "should be stored off-chain," endorse "cryptographic commitments, keyed hashes, or references," and treat erasure as making data "effectively unidentifiable" ([Mondaq](https://www.mondaq.com/fin-tech/1617044/blockchain-and-gdpr-edpb-guidelines-022025-adopted)). They also warn that encryption "will be overtaken by time" and that infrastructure choice "cannot be used as a reason not to comply" ([PPC Land](https://ppc.land/european-data-watchdog-issues-blockchain-processing-guidelines/)). Crypto-shredding (per-subject keys destroyed on erasure) is defensible but not settled. Verraes quotes the counter-view that "encrypted personal data is still personal data" and recommends **Forgettable Payloads**, where personal data sits in a deletable side store referenced from events ([Verraes](https://verraes.net/2019/05/eventsourcing-patterns-throw-away-the-key/); [Forgettable Payloads](https://verraes.net/2019/05/eventsourcing-patterns-forgettable-payloads/)). The ICO adds three operational rules: backups can be put "beyond use" until overwritten, erasure is due within one month (extendable by two), and the legal-claims and legal-obligation exemptions are the basis for legal hold ([ICO](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)). The event log is not the only copy. Outbox rows, Temporal histories, search indexes and AI caches all need the same treatment.

| Objection | Evidence | What survives |
|---|---|---|
| Single container is too rigid | Drive moved *to* single-parent plus shortcuts | **Survives**, if links/shortcuts are references that never leak target title or fields |
| Narrow-only blocks real sharing needs | JSM participants, Linear shared issues, Drive direct grants | **Inheritance survives; "no widening at all" does not.** Add explicit audited grants |

## The concrete policy model

### Scopes and grants combine as a tree plus a union

A **scope** is a node in a tree that mirrors containment. Every container (Space, Project, Queue) is a scope root. An Item becomes its own scope only when it narrows read access (for example, "internal only") or carries direct grants. Every other Item points at its nearest ancestor scope. A scope has two parts. The first is a **narrowing filter**, a predicate over principal attributes and roles such as `kind = member AND role IN (agent, lead)`. It is a filter, not a list, so it narrows whatever the parent allows. The second is a **grant set**: explicit `(principal or group, permission, granted_by, reason, expires_at)` rows. Effective readers resolve recursively:

```
readers(S) = (readers(parent(S)) ∩ narrow(S)) ∪ grants(S)
allowed(P, action, item) = tenant_fence(P, item)
                         ∧ P ∈ readers(scope(item)) for action
                         ∧ type_rule(action, item, P)
                         ∧ agent_cap(P, action, item)        -- agents only
```

Inheritance therefore never widens. Widening exists only in `grants(S)`, which is visible, audited, bounded by tenant policy, and flows down to descendants unless a descendant narrows it away. This is how a helpdesk ticket can be shared with a customer's colleague while an internal-note child scope ("members only") still excludes that customer. Tenant-level ceilings decide which grant kinds are allowed at all: guests on or off, external customers only within their own organization, public links **off by default**, maximum expiry, reshare disabled. Grants on Items inside a narrowed scope require scope-admin permission.

### The index carries scopes, not people

Search keeps the shape from the earlier search work: each Item document carries `tenant_id`, `scope_id` and a `tenant_readable` flag. Because grants live on scope nodes, a granted Item simply gets its own `scope_id`, and the user's visible set gains that ID. No per-person lists go on documents. `VisibleScopes(P)` expands the principal's groups (a Leopard-style user→groups table), walks the scope table, caches the result with a policy-version key, and is filtered as `tenant_readable OR scope_id IN (...)`. Design for **at most about 10,000 visible private scopes per user**, which matches AuthZed's threshold for filtering on an accessible-ID set. Above that, use selective-query-then-bulk-check. Every response's top 10–50 hits are re-checked against live Postgres policy, so revocation is immediate even while the index lags. Adding or removing a grant on a non-scope Item repoints only its subtree (usually a ticket and its comments). Adding or removing a member of a scope rewrites zero documents.

### Moves recompute in one transaction and refuse to widen silently

A move is a privileged action requiring manage rights at both source and destination, as Drive requires share access. In one transaction, the kernel re-parents the Item, repoints `scope_id` for descendants that inherited from above the moved node, and emits one event per repointed Item for the indexer. If the moved Item is itself a scope root, only its parent pointer changes. **Direct grants travel with the Item. Inherited access is recomputed.** Before committing, the kernel compares readers before and after the move. If the set grows, the move needs explicit confirmation, and from a narrowed scope into a tenant-readable one it is blocked unless an admin overrides. This mirrors GitHub's private-to-public rule. If the Item's narrowing filter references roles or groups that don't exist in the destination, the move is rejected with a reason, never orphaned (Jira's two bugs). Cross-tenant moves do not exist.

### Field projection runs on every outbound path

Types declare field rules once: a read class and a write class per field (for example `salary: read=finance`, `internal_note: read=members`), plus whether the field is externally writable, which marks it untrusted for agents. A single `Project(principal, item, purpose)` function produces every outbound representation: API and UI responses, search documents (restricted values go into a sub-document with a narrower scope and never into shared text, snippets or embeddings), exports, notification and email templates, webhooks, outbox payloads, event-log reads, agent context assembly, and Temporal inputs. Temporal receives IDs, not field values. Redacted fields return an explicit `{redacted: true}` marker. Filtering, sorting and faceting on a field the viewer cannot read is rejected, because "salary > X" leaks the value. A CI coverage test enumerates every serializer and fails if one bypasses `Project`. That test is the defense against the GitLab and Copilot failure mode.

### External users get exactly their grants and nothing else

Customers and guests are a principal kind whose visible scopes are **only** their explicit grants and organization memberships. They get no tenant defaults, no directory browsing, no group mentions and no app installs. A customer's own tickets are scopes granted to them, and organization-wide visibility is a grant to the customer-organization group, as in Zendesk. A widened Item hides its container metadata (team, project, cycle), as Linear does. References rendered to externals are permission-checked on the target, so a mention never leaks a title. An admin "external exposure" report lists every grant to a non-member and every public link, with expiry.

### Agent rules

| Rule | Mechanism |
|---|---|
| Identity | Agent is a principal with a required human **sponsor**; lifecycle events (disable, delete, sponsor leaves) cascade to its grants |
| Delegated mode | Effective = user's rights ∩ agent's grant (scopes, Types, actions); never a union, never a service role |
| Own-identity mode | Admin-granted scopes only, for automations; no tenant-wide default |
| Autonomy | Per transition: act, propose, or require approval; high-risk and outward-facing transitions default to propose |
| Separation of duties | Approver cannot be the proposing agent, the on-behalf-of user, or anyone in the delegation chain |
| Egress gate | A write whose audience is wider than the scopes the agent read in this session (public reply, external comment, email, webhook, rendered external URL) requires approval |
| Untrusted input | Content from externally writable fields is tagged; sessions that read it cannot act autonomously on egress transitions |
| Attribution | Every event records `actor`, `on_behalf_of`, `agent_session`, and the Item IDs in the agent's context |
| MCP boundary | OAuth resource server, audience-bound tokens, issuer validation; map IdP delegation claims onto `actor` / `on_behalf_of` |
| Quotas | Per-principal-kind rate limits and budgets (no vendor precedent found; set your own) |

### Explain-access is an API, not a support ticket

Because effective access is an intersection along the ancestor chain plus a union of grants, "why can't I see this" is hard to answer without tooling. `Explain(principal, action, item)` returns the decision, the scope chain with each node's narrowing filter and whether the principal passed it, the grant that admitted them if any, the Type rule result, the field projections that would apply, the agent cap if relevant, and the policy version. `WhoCan(action, item)` returns the resolved principal set with the path that admitted each one. That serves access reviews, the move-widening check and admin debugging. Figma's expression-tree debugger is the model. Decisions on sensitive actions log the same structure.

### Audit and erasure design

The event log stores opaque principal and Item IDs, operation type, field paths, policy version and the attribution fields above. Personal free-text and PII values go to a deletable payload store referenced by ID, or are encrypted under per-subject keys where moving them off-log is impractical. Entries are hash-chained over the envelope so tampering is detectable while payloads stay erasable. Erasing a person deletes their directory mapping (name, email) and their payload rows or keys. History still shows "principal P did X," which is pseudonymous. A **legal hold** flag on a tenant, Item or principal suspends retention deletion and erasure execution, and logs the request and the exemption relied on. Erasure fans out as a tracked job to the outbox, search index, embeddings and AI caches, and Temporal. Temporal is handled by passing only IDs and keeping namespace retention short. Retention classes are declared per Type, which gives the differentiated deletion the Berlin DPA asked for. Access-review exports list each principal, human and agent separately, with sponsor, grants, last use and delegation mode. Recertifications are themselves events.

## Temporal costs about a quarter-cent per ticket, and storage is the surprise

Temporal Cloud bills per Action. Starts, signals, updates, queries, timer starts, activity attempts and server-reaching heartbeats each cost one, Child Workflows cost two, and Signal-With-Start costs one whether or not it starts anything. Replays and deduplicated starts are free ([Temporal Actions](https://docs.temporal.io/cloud/actions)). The Developer plan pays **$50 per million flat plus 10%**. Business pays the greater of $500 or 10% of usage, on tiers falling from $50 to $25 per million up to 200M Actions. **Active storage (open workflows) costs $0.042/GBh, 40 times the $0.00105/GBh rate for Retained storage** ([Temporal pricing](https://docs.temporal.io/cloud/pricing)). High-availability namespaces double both.

The worked estimate below is the research's own model, not a published figure. A helpdesk ticket with SLA warn and breach, two customer-wait pauses, a nudge, a 7-day auto-close, one approval and four state write-backs comes to **about 32 Actions** (lean design about 20, heavy design with retries and UI queries about 60). About 13 of those 32 are timer starts.

| Actions/ticket | Tickets/month | Developer ($50 + 10%) | Business tiered + 10% | Best self-serve rate ($25/M) |
|---|---|---|---|---|
| 32 | 100K | $176 | $500 minimum | $80 |
| 20 | 1M | $1,100 | $963 | $500 |
| 32 | 1M | $1,760 | **$1,425** | $800 |
| 60 | 1M | $3,300 | $2,448 | $1,500 |
| 32 | 10M | $17,600 | $9,818 | $8,000 |

Storage changes the picture. No source publishes bytes per history event. Assuming 100–150 events at 0.3–1 KB each, a ticket history is **50–250 KB**. Held open for about 10 days by the auto-close tail, that costs **$480–$2,400 of Active storage per million tickets**, plus $72–$541 Retained depending on size and retention. Temporal says storage is "typically 10% or less" of the bill ([cost optimization](https://docs.temporal.io/best-practices/cost-optimization)). For mostly idle entity workflows this model puts it at **40–70% of Action cost**. All-in, 1M tickets/month on Business comes to about **$2.5K–$2.7K/month, about $0.0025 per ticket**, or about $5K with HA. The levers are small payloads (IDs only, which projection and erasure require anyway), Continue-As-New before long sleeps to move history into the cheap Retained tier, and one "next deadline" timer recomputed on each signal instead of parallel timers.

The limits that matter are a **default 500 Actions/sec per namespace** (about 1.3B/month sustained, or roughly 40M tickets at 32 Actions, though bursts are the real constraint), 51,200 events or 50 MB of history per workflow, 10,000 signals and 2,000 updates per execution, 10 in-flight updates, and 1–90 days of retention. No limit on open workflows is published ([Temporal limits](https://docs.temporal.io/cloud/limits)). A ticket at about 150 events sits roughly 340 times below the history cap, so Continue-As-New is a storage-tiering tool here, not a necessity. Bulk imports and mass SLA recalculations should add jitter to timers so they don't all fire in the same second.

Self-hosting removes Action fees, but the operational traps are documented. The shard count is fixed at build time, Temporal ships no control plane, RBAC or audit logging, upgrades go through each minor version in sequence (releases can be biweekly), and Temporal guarantees no support for server versions ([Temporal checklist](https://docs.temporal.io/self-hosted-guide/production-checklist)). "There isn't a prescriptive guide to sizing PostgreSQL for Temporal" ([Temporal forum](https://community.temporal.io/t/postgres-db-instance-sizing-recommendations/3500)). The only cost comparison found is a low-reliability third-party estimate of **$2.5K–$4.5K/month of infrastructure plus 0.25–1 FTE**, with break-even somewhere between 30M and 100M Actions/month. The article gives both ranges, and it misstates Cloud's starting price ([Automation Atlas](https://automationatlas.io/guides/temporal-cloud-vs-self-hosted-2026/)). At 1M tickets/month (about 32M Actions) self-hosting does not pay for itself. Start on Cloud.

Switching vendors won't save much. Inngest bills $25–$50 per million executions, DBOS $40–$50 per million checkpoints, and Restate Cloud counts durable sleeps as actions ([Inngest](https://www.inngest.com/pricing); [DBOS](https://www.dbos.dev/pricing); [Restate](https://www.restate.dev/pricing)). The real alternative is a **Postgres timer table**: `timers(item_id, kind, due_at)` with a `due_at` index and a `FOR UPDATE SKIP LOCKED` poller. Marginal cost is close to zero, but you own pause/resume, idempotency and multi-instance claiming. Its claimed capacity of millions of pending timers on one instance is the research's estimate, not a sourced figure. The hybrid worth testing in the spike: simple deadlines (nudge, auto-close, SLA warn and breach) live as rows; when one fires, it writes an outbox event that lazily wakes the Item's workflow; and workflows close when idle. That removes most timer Actions and most Active storage, at the cost of more starts. Nango took this direction to the extreme and left Temporal for a Postgres orchestrator because its workload couldn't use durable resumption ([Plushcap summary](https://www.plushcap.com/content/nango/blog/nango-migrating-from-temporal-to-a-postgres-based-task-orchestrator)). EvenUp, Atlan, Vantage and Turo moved the other way and reported benefits ([Atlan](https://blog.atlan.com/engineering/argo-to-temporal-migration/); [Turo](https://medium.com/turo-engineering/quartz-to-temporal-modernizing-job-scheduling-at-turo-7e120b98472c)). Keeping Postgres as the source of truth keeps both exits open.

## Hand off with a per-Item relay and a sequence watermark

A global outbox cursor is the classic trap. Sequence values are assigned before commit, so a poller advancing `id > last_id` can **skip a row from a slower transaction that commits later** ([event-driven.io](https://event-driven.io/en/ordering_in_postgres_outbox/)). Gunnar Morling says this "cannot be solved generically with concurrent writers when polling" and prefers log-based CDC, which emits in commit order. He also argues that a **monotonic watermark beats an ID journal** for consumer deduplication ([morling.dev](https://www.morling.dev/blog/revisiting-the-outbox-pattern/)). The kernel sidesteps the cursor problem. It assigns `seq = item.last_seq + 1` under the Item's row lock, so per-Item seq order equals per-Item commit order with no gaps, and the relay tracks progress **per Item**, never through a global high-water mark. A `delivered_at IS NULL` flag with `SKIP LOCKED` finds pending work without a cursor. CDC (Debezium, logical replication) brings slot and WAL-retention risk and is not worth it at moderate volume. Temporal's community guidance matches this DB-first shape: a consumer reads the outbox and routes rows to workflows, using signal-with-start for lazy creation ([Temporal forum](https://community.temporal.io/t/using-external-db-events-to-drive-workflows-in-temporal/13363)).

The handoff has three layers. Workflow ID `item-<id>` guarantees **at most one open run per Item** ([Temporal docs](https://docs.temporal.io/workflow-execution/workflowid-runid.md)). Each event is delivered with **Update-With-Start**, `WorkflowIDConflictPolicy = USE_EXISTING`, a deterministic `UpdateID = "<itemID>:<seq>"`, and `WaitForStage = Accepted`. The relay marks the outbox row delivered only after the event is durably in workflow history. Inside the workflow, a **`lastAppliedSeq` watermark** makes duplicates (`seq ≤ lastApplied`) accepted no-ops, so the relay sees success. A validator rejects gaps (`seq > lastApplied + 1`) without writing to history, so the relay retries from its lowest undelivered seq. The watermark is required because the server deduplicates Update IDs **per run only**, signal request-ID deduplication isn't exposed to application code, and neither survives Continue-As-New ([Handling messages](https://docs.temporal.io/handling-messages); [Temporal forum](https://community.temporal.io/t/thoughts-on-implementing-kafka-exactly-once-messaging-integration/13495)). Use a single `ApplyEvent` message type, because registering handlers for different types can reorder buffered messages across types ([Go message passing](https://docs.temporal.io/develop/go/workflows/message-passing.md)).

| Decision | Choice | Why |
|---|---|---|
| Start primitive | Update-With-Start, USE_EXISTING | Positive ack at Accepted; validator can reject gaps without polluting history |
| Fallback | Signal-With-Start | Atomic and 1 Action, but no ack and no validator; workflow must still dedupe |
| Non-atomicity | Accept it | Update-With-Start can start a workflow even if the update fails; the retry with the same Update ID heals it ([Early Return](https://docs.temporal.io/design-patterns/early-return.md)) |
| Start input | No event, only `fromSeq` | Events always arrive through the update path, so one ordering rule applies |
| Relay concurrency | One in-flight delivery per Item, any number of Items in parallel | Per-Item FIFO without a global cursor |
| Inline fast path | After commit, kernel tries the same Update-With-Start best-effort | Low latency; the watermark absorbs the duplicate when the relay retries |
| Continue-As-New | `Await(AllHandlersFinished)`, drain pending messages, pass `lastAppliedSeq` and state as input | Prevents lost messages and lost dedupe |
| Closed workflows | ALLOW_DUPLICATE reuse; new run hydrates state and `lastAppliedSeq` from Postgres via an activity | Signals and updates to closed runs fail; reuse policies only see runs within retention |
| Outbox retention | Keep delivered rows at least as long as namespace retention | The outbox is the replay source for resets |

Two evidence gaps affect this design directly. The Go SDK changelog lists Update-With-Start only as a **pre-release from October 2024**. The docs present it as a normal feature and recommend Server 1.28 or later, but no GA date was confirmed. No public production write-up was found of a Postgres outbox feeding Temporal through Update-With-Start, and no official sample of a seq-ordered relay exists. Standalone Activities (GA September 2026) and Nexus don't solve the handoff: enqueuing a durable job after commit is just another dual write ([Temporal changelog](https://temporal.io/changelog/standalone-activities-durable-job-processing-ga)).

## What the kernel spike must measure

| Area | Measurement | Pass signal |
|---|---|---|
| Actions | Real Action count per ticket lifecycle, by design (parallel timers vs single deadline vs Postgres timer table) | Near or below 32; know the timer share |
| History size | Bytes per closed history with ID-only payloads | ≤ 100 KB per ticket |
| Storage mix | Active vs Retained GBh with and without Continue-As-New before long sleeps, and with close-when-idle | Storage ≤ 30% of Action cost |
| Handoff latency | Commit → Accepted, p50/p99, inline path vs relay only | p99 within the product's tolerance; relay p50 near its poll interval |
| Correctness | Inject duplicate, out-of-order and gapped deliveries; kill the relay and workers mid-flight; run Continue-As-New with updates in flight; send an event to a closed run | Zero lost, zero double-applied, order preserved |
| Update-With-Start | Behavior on target server version (≥1.28) and Go SDK; no worker available; retries | Self-heals with the same Update ID |
| Burst | Bulk-import 100K Items with timers against the 500 APS default | Jitter prevents throttling; know the provisioning need |
| Visible scopes | `VisibleScopes` latency for users with 10, 1,000 and 10,000 scopes; cache hit rate | p99 ≤ 10 ms cached |
| Moves | Move a subtree of 10K Items; time to repoint and reindex; widening check | One transaction; stale window covered by top-k recheck |
| Projection coverage | Every serializer routed through `Project`; restricted field never in search text, embedding, webhook or Temporal payload | CI test fails on bypass |
| Agent flow | Delegated agent reading customer content tries to post externally | Blocked or routed to approval; full attribution recorded |
| Erasure drill | Erase a principal and verify log integrity, payload deletion, index and cache purge, Temporal residue | Hash chain intact; no PII remaining after retention |

## Conclusion

The search work identified permission compression as the kernel's main advantage. This research adds one refinement: compression and widening are compatible as long as widening is modeled as **grants that attach to scope nodes, not as exceptions on individual documents**. That keeps one `scope_id` per Item, keeps ancestor membership changes free, and limits the cost of sharing to re-pointing small subtrees. Products that skipped this (Jira with participants, Notion with broadest-wins) ended up either blocking a core use case or losing the ability to narrow. The same structure that makes search cheap also makes the agent problem tractable. Because every Item's audience is a computable scope, the kernel can compare "what the agent read" with "who will see what it writes", which is information-flow control that most vendors have only patched in afterward with URL allowlists.

On runtime, cost is not the deciding factor at a quarter-cent per ticket. Correctness at the handoff and the number of data copies are. Each Temporal history, outbox row and index entry is another place where field rules and erasure must reach, so the cheapest design is also the safest one: IDs-only payloads, short retention, Postgres as the single source of truth, and workflows that stay open only while they are actually coordinating something. The spike should be judged less on throughput than on whether the duplicate, gap, closed-run and erasure drills pass without special cases.
