# Keep the commit pure, push code outward

Every product family surveyed sorts its extension points into the same five timing tiers. Gates run before the write. Validators and mutators run inside the transaction. Reactions run after the write but before commit. Asynchronous reactions run after commit. Scheduled rules run later. Only the names differ. Jira says condition, validator and post-function. ServiceNow says before, after and async business rule. Salesforce says before-save flow, trigger and async path. Camunda says listener and job worker. Orleans says grain call filter. "Trigger" alone means three incompatible things. The industry's direction of travel supports the kernel's tentative rule that nothing user-defined runs inside the write transaction except CEL. **Kubernetes moved the common admission case from webhooks to in-process CEL** and kept webhooks as an escape hatch. **Shopify lets third-party code run on checkout only as metered, network-free WebAssembly.** Camunda 8 reportedly removed in-process user code entirely and Salesforce consolidated three automation engines into Flow, though the Camunda details are unverified prior knowledge. The products that do run code inside the write paid for it with recursion caps (Salesforce trigger depth 16, Jira loop detection at 10), shared per-transaction budgets, ordering they explicitly do not guarantee, and customizations that break on upgrade. **Orleans grains do have these concepts, but only as platform interceptors and lifecycle participants, not as per-type domain hooks.** Incoming and outgoing grain call filters can deny a call, rewrite its result and translate exceptions. Orleans has no notion of validator versus post-function, no causation, and no declarative connector configuration. That leaves the kernel's open questions narrower than "where does code run." Should a blocking tier sit beyond CEL? How should loops be stopped by causal lineage rather than by counts? How should principal, on-behalf-of and originating hook be recorded? How should hook code pin to Type versions? How should connectors package code, templates and scoped secrets? How should connector-delivered text be kept from steering agents? Much of the BPM, actor-runtime and low-code detail below comes from notes whose researchers could not re-read the pages. Those claims are marked **(unverified)** wherever they appear.

**How to read the evidence.** Unmarked claims come from pages that a researcher fetched and read during this research. **(unverified)** marks a claim that rests on the researcher's prior knowledge. The linked page is the canonical location, but nobody re-read it during this research. Almost all of the Camunda, Flowable, Pega, Appian, n8n, Zapier and Kafka Connect material falls in this category. So does the Orleans material beyond call filters and lifecycle (timers, reminders, JournaledGrain, streams, grain extensions), all of Pekko, Restate, Durable Objects and Durable Entities, and Dapr beyond bindings. ServiceNow Flow Designer and IntegrationHub, Shopify's checkout failure behavior, Stripe beyond the secondary Hookdeck guide, and Hasura Actions are also unverified. Several webhook-semantics claims come from secondary guides (Hookdeck, OneUptime) and are labeled as secondary.

"Trigger" deserves special mention. In Salesforce it means synchronous Apex inside the save. In Zendesk it means a post-update rule cycle. In Forge it means an asynchronous event subscription. In Airtable and Zapier it means the event source that starts an automation. The kernel should not use the bare word.

## Where code runs relative to commit decides its limits

The timing model has five positions plus a sixth that only the BPM engines use: the held transition. The table gives examples from every family, then the limits each family attaches to each position.

| Position | Trackers, ITSM, CRM | BPM and low-code | Actor and durable runtimes | Customer-code platforms | Typical limits and failure mode |
|---|---|---|---|---|---|
| **Before write**, outside any transaction | Jira condition hides a transition; ServiceNow display rule | Pega when rule on visibility (unverified) | Orleans incoming filter throws to deny; Temporal client interceptor | Envoy ext_authz (200 ms default gRPC timeout); K8s `matchConditions` | Remote calls need a fail-open or fail-closed switch |
| **In transaction, before the row is written** | Jira validator; ServiceNow before rule (can abort); Salesforce validation rules, before-save flows, before triggers; YouTrack guard and action | Camunda 7 and Flowable listeners and delegates (unverified); Pega Declare Expression (unverified) | Orleans grain method; Temporal update validator (rejected updates leave no history; unverified detail) | K8s CEL policies; Shopify Function; Auth0 Action (20 s); Okta inline hook (3 s, 1 retry) | Shared per-transaction budget; row locks held; errors abort the write |
| **In transaction, after the row is written but before commit** | Salesforce after triggers, workflow rules, after-save flows, roll-ups; ServiceNow after rule | Pega Declare Trigger "immediate" (unverified) | Pekko `thenRun` runs after persist succeeds (unverified) | — | Recursion: writes here re-enter the pipeline |
| **Held: transition pending until an external worker answers** | — | Camunda 8 user task listeners: task sits in `ASSIGNING`/`COMPLETING` until worker allows, denies or corrects (unverified) | Temporal Update waiting on an activity | — | Caller may time out while the transition later completes; stuck states become incidents |
| **After commit, asynchronous** | Forge post-functions and product events; ServiceNow async rule; Salesforce async Apex, async paths, CDC; Zendesk, Linear webhooks | Camunda 8 job workers and outbound connectors; Airtable, Notion, n8n, Zapier automations (unverified detail) | Temporal activities; Orleans streams; Dapr output bindings | Okta event hooks; Hasura event triggers; Supabase database webhooks | At-least-once, duplicates, no ordering guarantee; receiver timeouts 3–10 s |
| **Scheduled** | YouTrack on-schedule; Zendesk automations (hourly, unverified); Salesforce scheduled paths (batch 200) | Zapier polling triggers every 1–15 min (unverified); Retool schedules (unverified) | Orleans reminders (persistent) vs timers (volatile) (unverified); Temporal durable timers | Cloudflare cron (not researched) | Must not re-fire forever; Zendesk requires a nullifying condition (unverified) |

Sources: [Envoy ext_authz](https://www.envoyproxy.io/docs/envoy/v1.11.0/configuration/http_filters/ext_authz_filter), [Okta hooks](https://developer.okta.com/docs/guides/hooks-best-practices/), [Auth0 Actions limits](https://auth0.com/docs/customize/actions/limitations), [Salesforce Architects decision guide](https://architect.salesforce.com/decision-guides/trigger-automation), [Camunda user task listeners](https://docs.camunda.io/docs/components/concepts/user-task-listeners/) (unverified), [Hasura via Hookdeck](https://hookdeck.com/webhooks/platforms/guide-to-hasura-webhooks-features-and-best-practices.md) (secondary), [Supabase database webhooks](https://supabase.com/docs/guides/database/webhooks).

Salesforce publishes the most complete map of the in-transaction region, and it shows how crowded that region gets. One save runs system validations, before-save flows, before triggers, custom validation and duplicate rules, the uncommitted write, after triggers, assignment and auto-response rules, workflow rules, escalation rules, after-save flows, entitlement rules, parent and grandparent roll-ups that each re-enter the save, and sharing evaluation. Only then does it commit. **Email, queued async Apex and flow async paths wait until after commit** ([Salesforce](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm)). All of that in-transaction work shares one budget: **100 SOQL queries, 150 DML statements, 10,000 ms CPU, 10 MB heap and a trigger stack depth of 16** for synchronous transactions ([Salesforce limits](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexref/apex_gov_limits.htm)). The budget is per transaction, not per hook, so one slow customer hook can exhaust it for every other hook on the same write.

YouTrack shows the cleanest in-transaction semantics. All changes from one request form a single database transaction. Before commit, YouTrack checks the guards of the project's rules, adds any workflow changes to the same transaction, and **re-checks guards "until none are satisfied"** before committing ([YouTrack](https://www.jetbrains.com/help/youtrack/devportal/workflow-transactions.html)). That is a fixpoint, and YouTrack documents no iteration cap. Zendesk runs a similar loop after the update but adds the missing rule: a trigger "fires at most once per cycle," and the cycle restarts when a trigger changes the ticket ([Zendesk](https://support.zendesk.com/hc/en-us/articles/4408886797466-Managing-your-ticket-triggers)).

The customer-code platforms make the timing trade-off explicit, which is why they are the most useful comparison for the kernel. Two families of synchronous hook exist. **The first is platform-hosted, deterministic and metered.** Shopify Functions run up to **11 million Wasm instructions** for carts of up to 200 lines, binaries are capped at 256 KiB, and instruction counts are deterministic, so the same module and input always cost the same. Overruns fail with `InstructionCountLimitExceededError` ([Shopify](https://shopify.dev/docs/apps/build/functions/optimize-instruction-counts)). Kubernetes CEL policies charge a cost that "depends only on the input and the expression," which the KEP calls "less of an availability concern than webhook timeouts" ([KEP-3488](https://www.kubernetes.dev/resources/keps/3488/)). **The second family is customer-hosted and remote, with a short timeout and a fail-open or fail-closed knob.** Okta inline hooks get 3 s and one retry, and "the user experience pauses until your endpoint responds" ([Okta](https://developer.okta.com/docs/guides/hooks-best-practices/)). Kubernetes admission webhooks accept 1–30 s with a 10 s default ([OneUptime](https://oneuptime.com/blog/post/2026-02-09-webhook-failure-policy-timeout/view), secondary). Envoy ext_authz defaults to a 200 ms gRPC timeout with `failure_mode_allow` as the switch ([Envoy](https://www.envoyproxy.io/docs/envoy/v1.11.0/configuration/http_filters/ext_authz_filter)). Auth0 Actions sit between the two: platform-hosted Node.js with network access and a **20 s** limit per trigger execution ([Auth0](https://auth0.com/docs/customize/actions/limitations)). A 20 s hook holding Postgres row locks is incompatible with a busy Item table. A millisecond, no-I/O budget is compatible.

**Kubernetes is the clearest precedent for the kernel's rule.** KEP-3488 moved the common admission case in-process with CEL: alpha in 1.26, beta in 1.28, GA in 1.30. MutatingAdmissionPolicy followed and is stable in v1.36 ([Kubernetes docs](https://kubernetes.io/docs/reference/access-authn-authz/mutating-admission-policy)). The KEP gives three reasons. Webhooks "contribute to latency by requiring another network hop." Their extra infrastructure forces operators to choose between failing closed (hurting availability) and failing open (weakening enforcement). They are "operationally burdensome" to observe, secure and roll out. Webhooks were kept as an escape hatch, and CEL is explicitly not expected to make external calls ([KEP-3488](https://www.kubernetes.dev/resources/keps/3488/)). In-process validation defaults to fail closed, which is safe because a failure means a buggy policy rather than an outage. Mutating policies return an ApplyConfiguration or a JSONPatch that the API server applies. They never write directly ([Kubernetes docs](https://kubernetes.io/docs/reference/access-authn-authz/mutating-admission-policy)).

Camunda 8 tells a similar story from the BPM side, though every detail here is **(unverified)** prior knowledge. Zeebe reportedly runs no user code in-process. Every service task and listener becomes a job that an external worker activates, completes, fails or answers with a BPMN error, and FEEL is the only in-engine language ([Camunda conceptual differences](https://docs.camunda.io/docs/guides/migrating-from-camunda-7/conceptual-differences/); [Camunda blog](https://camunda.com/blog/2022/02/how-to-write-glue-code-without-java-delegates-in-camunda-cloud/)). Camunda 7, by contrast, ran listeners and delegates inside the engine's database transaction. A thrown exception rolled back to the last wait state. BPMN referenced a class name, but the code was not versioned with the process, so **old instances ran whatever class was on the classpath** ([Camunda 7→8 listener patterns](https://github.com/camunda/camunda-7-to-8-migration-tooling/blob/main/code-conversion/patterns/30-glue-code/30-java-spring-listeners/listeners.md), unverified). When Camunda 8 restored execution listeners (8.6) and user task listeners (8.7–8.8), it did so **as blocking remote jobs, not in-process code**. A task listener holds the task in a transitional state and can complete with `deny: true`, an optional reason, or "corrections" to assignee, due date, candidate groups and priority ([Camunda user task listeners](https://docs.camunda.io/docs/components/concepts/user-task-listeners/), unverified). This held-transition pattern is the closest existing model for a remote allow, deny or correct hook. Its cost shows in a Camunda issue titled "Document 504 response scenarios for Complete user task API": the caller can time out while the transition still completes later ([camunda #44179](https://github.com/camunda/camunda/issues/44179), title only).

## Orleans grains have interceptors and lifecycle, not domain hooks

**Yes, Orleans grains have extension points of this kind, but they sit at a different level from Jira validators or Camunda listeners.** Orleans gives platform and application developers code-level interception around every grain call. It does not give end users declarative, per-type hooks. Here is what Orleans has, mapped onto the vocabulary above.

The **incoming grain call filter** (`IIncomingGrainCallFilter`) is the validator, condition and interceptor rolled into one. It runs on the silo before the grain method, has a single async `Invoke(ctx)` method, and can modify `RequestContext`, arguments and the return value. Throwing before `ctx.Invoke()` denies the call; the docs' example throws `AccessDeniedException` unless an `isAdmin` flag is set. Setting `ctx.Result` after `await ctx.Invoke()` rewrites the result; the docs' example changes 7 to 38. Catching the exception and not rethrowing marks it handled. Ordering is explicit: DI-registered filters run "in the order in which they are registered," then the grain's own filter if the grain class implements the interface, then the method. Each filter wraps the next, so the chain behaves like an onion. Filters run "for all method calls to a grain, including calls to grain extensions." The docs also note that authentication is the caller's job, and filters only enforce authorization ([Orleans grain call filters](https://learn.microsoft.com/en-us/dotnet/orleans/grains/interceptors)). One documented wrinkle: `Arguments` is a get-only array, so filters can mutate elements but cannot replace the array.

The **outgoing grain call filter** (`IOutgoingGrainCallFilter`) is the client-side or caller-side interceptor. It is used to stamp context such as tracing or opt-in flags, and it runs even on Orleans' own system calls. The docs warn that a filter calling other grains can recurse infinitely, and their sample excludes its own grain type to avoid this ([Orleans grain call filters](https://learn.microsoft.com/en-us/dotnet/orleans/grains/interceptors)). That is the same loop problem the trackers have, at a lower level.

The **grain lifecycle** (`ILifecycleParticipant<IGrainLifecycle>`) is a staged set of activation hooks: `First`, `SetupState` (load persisted state), `Activate` (`OnActivateAsync`/`OnDeactivateAsync`) and `Last`. Components subscribe "without adding any special grain logic." The docs warn that **"applications shouldn't rely on the grain lifecycle always executing during grain deactivations,"** because silo crashes skip it ([Orleans grain lifecycle](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-lifecycle)).

The rest of the Orleans model is **(unverified)**. Grain extensions (`IGrainExtension`) attach extra RPC interfaces to an existing grain and are mostly used by Orleans internals ([Grain extensions](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-extensions)). Timers are in-memory and tied to one activation, while reminders are persisted and reactivate the grain when they fire ([Timers and reminders](https://learn.microsoft.com/en-us/dotnet/orleans/grains/timers-and-reminders)). `JournaledGrain` has a pure `TransitionState` apply function that is replayed from the log, plus `OnStateChanged` callbacks after confirmed changes ([JournaledGrain](https://learn.microsoft.com/en-us/dotnet/orleans/grains/event-sourcing/journaledgrain-basics)). Persistence is extended by implementing or decorating `IGrainStorage`; there is no first-class "persistence filter" ([Grain persistence](https://learn.microsoft.com/en-us/dotnet/orleans/grains/grain-persistence/)). Streams with `[ImplicitStreamSubscription]` activate a grain when an event arrives, which is the Orleans version of an inbound connector and of "event arrives, lazily start actor" ([Orleans streaming](https://learn.microsoft.com/en-us/dotnet/orleans/streaming/)).

What Orleans **lacks** matters as much. It has no distinction between a validator, a mutator and a post-function. All three are code before or after `Invoke()`. It has no transaction that spans several hooks. It has no causation or "originating hook" metadata beyond whatever developers put in `RequestContext`. It has no versioned, declarative hook configuration attached to a grain type, no connector templates or secrets model, and no loop guard. Filters are .NET code registered at silo build time. That makes them a platform-author tool, plus a per-grain variant for application developers. They are not something a tenant administrator configures.

The other actor runtimes fall into two camps. **Temporal** matches Orleans with a full interceptor chain: client outbound (including `UpdateWithStartWorkflow`), workflow inbound (including a separate `ValidateUpdate` and `ExecuteUpdate`), workflow outbound, activity and Nexus interceptors. The Go interceptor docs warn that **"workflow interceptor methods also run during replay"** and must use replay-safe APIs ([Temporal interceptor package](https://pkg.go.dev/go.temporal.io/sdk/interceptor); [Temporal Go interceptors](https://docs.temporal.io/develop/go/workers/interceptors.md)). **Dapr** puts extension at the sidecar. Input bindings POST events to the app, where a 200 acknowledges and anything else schedules redelivery. Output bindings are `POST /v1.0/bindings/<name>` calls with an operation, and delivery is "exactly once or at least once" depending on the component ([Dapr bindings](https://docs.dapr.io/developing-applications/building-blocks/bindings/_print/)). Dapr's HTTP middleware pipeline, its .NET actor pre and post hooks, and its CEL-based pub/sub routing are **(unverified)** ([Dapr middleware](https://docs.dapr.io/operations/components/middleware/)). **Pekko, Restate, Cloudflare Durable Objects and Azure Durable Entities** are all **(unverified)** and offer few interception hooks. There, validation is ordinary code in the command handler. Pekko does separate a pure, replayed event handler from `thenRun` side effects that run once after persist ([Pekko persistence](https://pekko.apache.org/docs/pekko/1.0/typed/persistence.html)).

For the kernel the mapping is direct. **The stateless Go service plus Postgres transaction plays the role of Orleans' incoming filter plus grain method**, so authorization, CEL validation and any internal interceptors belong there. The relay's Update-With-Start can carry trace and tenant headers through a Temporal client interceptor. Inside the per-Item workflow, any interceptor must be replay-safe. Auth or database-touching logic must never live in a workflow interceptor. The workflow's update validator should check only cheap invariants such as sequence gaps, which the earlier policy and relay design already uses. Orleans and Temporal both confirm the tentative rule that interceptors are a platform-internal concept. Neither exposes interceptors to tenants.

## Failure modes cluster in recursion, timeouts, ordering and drift

The failure evidence is consistent across vendors, and almost every guardrail was added after customers got hurt. The notes rank the documented pain in this order: recursion and loops, synchronous timeouts in the request path, implicit ordering, and upgrade drift from forked customizations. Webhook delivery, connector credentials and agent prompt injection form a second cluster.

**Recursion is universal, and hand-built guards fail.** Salesforce surfaces "Maximum trigger depth exceeded" at depth 16. The community's static-Boolean "already ran" flag is itself broken on batches over 200 records, and Apex Hours says plainly: "Static Boolean is an anti-pattern so please DO NOT USE" ([Apex Hours](https://www.apexhours.com/how-to-avoid-recursion-in-trigger/)). Salesforce's own workflow re-fire rule is "one more time, and only one more time," and a flow "does not re-fire on the same record within a transaction" ([Salesforce](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm); [Architects guide](https://architect.salesforce.com/decision-guides/trigger-automation)). Jira Automation stops a flow after **10 rapid self- or cross-triggers** and marks it `LOOP` ([Atlassian](https://support.atlassian.com/cloud-automation/docs/automation-service-limits/)). ServiceNow detects recursion caused by `current.update()` inside a business rule and logs an error ([ServiceNow](https://www.servicenow.com/docs/r/build-workflows/business-rules-classic/c_BusinessRules.html)). **No surveyed platform publicly documents loop detection by causal lineage.** They all count.

**Synchronous execution meets hard runtime caps.** Forge functions hit a 25 s limit. A developer who moved work to the async queue still saw the same timeout, retried in a loop, until Atlassian raised async invocations to 55 s ([Atlassian Developer Community](https://community.developer.atlassian.com/t/invocation-limits-for-a-forge-app-maximum-runtime-seconds-25/72555)). ScriptRunner for Jira Cloud caps scripts at 240 s and each API call at a fixed 30 s ([Adaptavist](https://docs.adaptavist.com/sr4jc/latest/get-started/limitations)). The lesson for a Temporal-backed design is subtle. **Moving work to async does not help if the async unit has a short hard timeout and the platform retries blindly, because the retry turns a timeout into a loop.**

**Ordering is "not guaranteed" almost everywhere.** Jira says of multiple post-functions on one transition, "the execution order is not guaranteed" ([Forge post function](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-workflow-post-function/)). Salesforce says the same of multiple triggers on one object and event ([Salesforce](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_triggers_order_of_execution.htm)). So does ServiceNow for async rules, and so does YouTrack for equal-priority rules. The Salesforce community answered with a whole convention, "one trigger per object" delegating to handler classes ([Apex Hours](https://www.apexhours.com/how-to-avoid-recursion-in-trigger/)). Salesforce itself later added flow trigger ordering and retired Workflow Rules and Process Builder, which left orgs merging several automation layers that had been firing on the same object ([Salesforce Ben](https://salesforceben.com/salesforce-announces-end-of-support-for-workflow-rules-process-builder)).

**Customizations that fork vendor behavior break on upgrade.** ServiceNow "skips" upgrade records that conflict with customized business rules, client scripts and workflows, and its own advice is to create custom versions instead of modifying out-of-box objects ([ServiceNow Community](https://www.servicenow.com/community/developer-blog/reducing-skipped-records-in-servicenow-upgrades/ba-p/3102307)). ScriptRunner scripts do not survive the move from Jira Data Center to Cloud unchanged, because Cloud scripts can import only standard Java 17 classes and must go through REST under fixed limits ([Adaptavist](https://docs.adaptavist.com/sr4jc/latest/get-started/limitations)). The Camunda 7 classpath problem (unverified) and a Camunda 8 issue titled "user task listeners added in target process are not invoked after migrating an active user task" ([camunda #53122](https://github.com/camunda/camunda/issues/53122), title only) show that versioned hooks still have migration edge cases.

**Webhook delivery is at-least-once and unordered, and receivers carry the correctness burden.** Stripe does not guarantee order, sends duplicates, retries for up to 3 days and then disables the endpoint ([Hookdeck on Stripe](https://hookdeck.com/webhooks/platforms/guide-to-stripe-webhooks-features-and-best-practices.md), secondary). GitHub wants a 2XX within 10 s, deduplication on `X-GitHub-Delivery`, and **the receiver to request redelivery after its own outage** ([GitHub docs](https://github.com/github/docs/blob/fa7be01fa0b70f29d6e3733b8f3a187217eb1325/content%2Fwebhooks%2Fusing-webhooks%2Fbest-practices-for-using-webhooks.md)). Zendesk's circuit breaker opens at 70% failures or more than 1,000 errors in 5 minutes, and **events during the pause are not replayed** ([Hookdeck on Zendesk](https://hookdeck.com/webhooks/platforms/guide-to-zendesk-webhooks-features-and-best-practices), secondary). Linear times out at 5 s, retries after 1 minute, 1 hour and 6 hours, and can disable a webhook until it is manually re-enabled ([Linear](https://linear.app/developers/webhooks)). Salesforce CDC is the counterexample. Events are durable for three days, replayable by ID and stored in commit order, and changes from one transaction share a `transactionKey` ([Salesforce CDC](https://developer.salesforce.com/docs/atlas.en-us.change_data_capture.meta/change_data_capture/cdc_subscribe_delivery.htm)). A replayable log is categorically more reliable than fire-and-forget pushes.

**Connector credentials are the blast radius.** In the Salesloft Drift campaign of August 2025, stolen OAuth refresh tokens for one connected app let an attacker query Salesforce data in **700+ potentially impacted organizations**. The attacker hunted for AWS keys and Snowflake tokens and **deleted query jobs to cover their tracks** ([The Hacker News](https://thehackernews.com/2025/08/salesloft-oauth-breach-via-drift-ai.html)). Supabase's documentation warns that dashboard-created database webhooks store the secret in the trigger definition, where it shows up in dumps ([Supabase](https://supabase.com/docs/guides/database/webhooks)). No verified case of a malicious Jira or Confluence Marketplace app in 2020–2026 turned up.

**Agents turn connectors into injection channels.** In May 2025 a malicious public GitHub issue hijacked an agent reviewing issues, which then leaked private-repo data through a public PR. Invariant Labs called it "a fundamental architectural issue that must be addressed at the agent system level" ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). In July 2026 "GitLost" did the same to event-triggered GitHub Agentic Workflows. The attacker "needs only to open a normal-looking issue," and the one-word prefix "Additionally" got past threat detection. Researchers said "this is not the kind of bug a patch closes" ([The Hacker News](https://thehackernews.com/2026/07/public-github-issue-could-trick-github.html)). Jira Automation already ships a Rovo Agent action, so **LLM agents are hook targets in work tools today** ([Atlassian](https://support.atlassian.com/cloud-automation/docs/automation-service-limits/)). No verified incident was found of an LLM *authoring* a hook that then misbehaved; that risk remains theoretical in these sources.

**Attribution loses the cause.** Jira Automation attributes a flow's changes to its "actor," by default a synthetic user called "Automation for Jira," and admins can set any user as the actor ([Atlassian](https://support.atlassian.com/cloud-automation/docs/what-is-a-rule-actor)). Users then ask how to "show name of automation in issue history" ([Atlassian Community](https://community.atlassian.com/t5/Jira-questions/Show-name-of-automation-in-issue-history/qaq-p/2876100)). Forge chooses per call between `asApp()` and `asUser()`. Linear's webhook `actor` can be a user, an OAuth client or an integration ([Linear](https://linear.app/developers/webhooks)).

The guardrails that held up share one property: they are structural rather than numeric.

| Guardrail | Where it works | What it buys the kernel |
|---|---|---|
| Pre-commit hooks return a patch or decision; the platform applies it | K8s ApplyConfiguration and JSONPatch; Shopify output operations; Okta inline-hook commands | The hook never holds a DB handle, so it cannot recurse inside the transaction; outputs are replayable and policy-checkable |
| Deterministic cost metering instead of wall-clock timeouts | Shopify instruction counts; K8s CEL cost budgets | A hook that passes in test passes in production; failures replay exactly (`shopify app function replay`) |
| Explicit fail-open or fail-closed per hook | K8s `failurePolicy`; Envoy `failure_mode_allow` | Makes the availability-versus-enforcement trade visible; K8s suggests Ignore first, then Fail after verification |
| Cheap pre-filter before an expensive hook | K8s `matchConditions` (KEP-3716); Forge event filter expressions (10,000 chars, ~50,000 steps) | Fewer hook invocations; less latency |
| Fire once per cycle, fixpoint with a cap | Zendesk once per cycle; YouTrack fixpoint; K8s `reinvocationPolicy: IfNeeded` (re-run detail unverified) | Bounded in-transaction derivation |
| Self-event suppression by default | Jira Automation ignores rule-caused events unless opted in; Forge `ignoreSelf`; `GITHUB_TOKEN` events start no new workflow run | Kills the commonest loop without lineage |
| No-op suppression | Hasura delivers UPDATE events only when the row changed (secondary); Zendesk logs only net changes | Stops ping-pong between two writers |
| Durable, replayable outbound log | Salesforce CDC (3 days, commit order) | Recovery is replay from a cursor, not lost events |
| Stable event ID for idempotency | Stripe, GitHub, Okta `eventId` | Receivers and activities dedupe |
| Auto-disable with owner notice | Stripe after 3 days; Linear | Contains broken endpoints |
| Declared requirements checked at attach time | YouTrack `requirements` | Hooks cannot be enabled against a schema they don't match |
| Version suffix on code references | Camunda job type `io.camunda:http-json:1` (unverified) | Pins code semantics, not only configuration |
| Extend, don't modify | ServiceNow guidance; Forge manifests | Upgrades don't silently skip customizations |

## Six design choices remain open for the Item kernel

The tentative rule is well supported: only CEL runs inside the transaction, post-functions run as workflow activities after commit, outbound connectors subscribe to the event stream, inbound connectors call the five operations, and interceptors stay internal. Kubernetes reached the same split after a decade of webhooks, and Camunda 8 reached it from the BPM side (unverified). The rule leaves six questions open. Each has real options.

### Choice 1: does a blocking tier exist beyond CEL?

Some decisions cannot be expressed in CEL. Examples include "is this customer's contract active in the billing system," "does this change pass the customer's own compliance service," and anything needing a lookup the kernel does not hold. Every surveyed platform eventually ships an escape hatch, and the question is what shape it takes.

| Option | How it works | Precedent | Gains | Costs |
|---|---|---|---|---|
| **A. Pure CEL only** | Guards, validators and (optionally) derivations in CEL; anything else is post-commit | K8s ValidatingAdmissionPolicy; Jira expression validators; Salesforce before-save flows | Deterministic, metered, fail-closed safe, no toolchain, row locks held for microseconds | External checks become post-commit "compensate or flag" reactions, which users experience as a write that succeeds and is then undone |
| **B. CEL plus sandboxed Wasm in the transaction** | Customer-supplied Wasm module, instruction-metered, no network, input snapshot in, patch or decision out | Shopify Functions (11M instructions, 256 KiB); Extism and Wasmtime fuel (unverified) | General-purpose compute with CEL's determinism; replayable | Toolchain, binary storage and versioning, a Wasm runtime in the Go service, and more attack surface; still no network, so the "external system" case is still unsolved |
| **C. Remote allow, deny or correct worker with a pending state** | The operation commits a *requested* sub-state; an external worker answers allow, deny(reason) or correct(fields); a second transaction finalizes or reverts; deadline then incident | Camunda 8 user task listeners (unverified); Okta inline hooks; K8s webhooks | Solves the external-lookup case without holding a transaction open | Two transactions per guarded operation; a visible pending state other actors can observe; the caller may time out before the outcome (Camunda #44179); needs fail-open or fail-closed, timeouts, incidents and idempotent workers |
| **D. A ladder: A by default, C as an opt-in escape hatch, B deferred** | CEL validate, CEL derive, then a remote check only where declared, with `matchConditions`-style pre-filtering | The K8s ladder, with webhooks retained | Matches where K8s landed; keeps the common path pure | Two mental models for authors; option C semantics still have to be designed properly |

Option C has a twist specific to the kernel. The earlier Types research already models **approvals as waiting steps completed by a token, by a human or an agent**. A remote allow, deny or correct check is structurally an approval whose approver is a worker with a deadline. Modeling the blocking tier as "an approval completed by a machine" would reuse the pending state, the SLA timer, the audit trail and the Temporal wait the kernel already needs, rather than inventing a second mechanism. The trade-off is semantic. Approvals are business-visible, while a compliance check might need to be invisible to the requester. Option B is attractive mainly if third-party developers need custom logic on a latency-critical path, as Shopify's checkout does. Shopify's checkout failure behavior (whether a failing function is skipped or blocks checkout) is **(unverified)**, so that precedent's exact fail mode is unknown.

A sub-question inside option A: may CEL **mutate**, or only validate? Kubernetes allows CEL mutation as merge-only patches, and Salesforce's before-save "fast field update" ran 10 to 20 times faster than Workflow Rules or Process Builder in Salesforce's bulk tests ([Architects guide](https://architect.salesforce.com/decision-guides/trigger-automation)). Kubernetes also recommends validation over mutation for "prevent-only" cases ([Kubernetes docs](https://kubernetes.io/docs/reference/access-authn-authz/mutating-admission-policy)). The choice is between validate-only, computed fields only (pure derivations of other fields, Pega Declare Expression style), or general CEL patches with a once-per-write fixpoint and a cap.

### Choice 2: how are loops prevented?

Pure CEL cannot recurse inside the transaction because it cannot write, which settles the in-transaction case for option A. Loops then come from post-commit reactions and connectors that call the five operations again.

| Option | Precedent | Gains | Costs |
|---|---|---|---|
| **Count caps** (N re-triggers in a window, then stop and mark LOOP) | Jira Automation (10); Salesforce depth 16 | Simple, catches everything eventually | Arbitrary threshold; the first nine iterations still happen; no explanation for users |
| **Self-suppression** (a reaction ignores events caused by itself, or by any rule, unless it opts in) | Forge `ignoreSelf`; Jira default; `GITHUB_TOKEN` | Kills the most common case cheaply | Misses two-hook ping-pong; opt-in becomes a footgun |
| **Causation lineage** (every operation carries `correlation_id`, `causation_id` = triggering event, and a hop count; refuse if the same hook would fire on the same Item twice in one chain, or hops exceed a cap) | No platform publicly documents this; it is a design opportunity | Exact cycle detection; a user-visible "why did this fire" trace | Every caller, including inbound connectors and agents, must propagate IDs; external round-trips (kernel → webhook → external system → inbound API) break the chain unless the connector echoes the ID |
| **No-op suppression** (no event if nothing changed) | Hasura (secondary); Zendesk net-change logging | Stops ping-pong between writers converging on the same value | Doesn't stop divergent oscillation |

These options compose rather than compete. A plausible stack is no-op suppression, then self-suppression by default, then a causation-lineage cycle check, with a hop-count cap as the backstop. The open question is how far lineage can reach. Inside the kernel and Temporal it is exact. Across an external system it depends on whether outbound connectors embed the causation ID in a way inbound connectors can recover.

### Choice 3: how is a hook's write attributed?

Every reaction that calls the five operations needs a principal for policy checks and a record for audit. Products split along three lines. Jira uses a single configurable actor, which loses the cause and lets admins pick any user. Forge picks as-app or as-user per call. Linear's webhook payloads carry an actor kind. The earlier policy research already settled on recording `actor`, `on_behalf_of` and `agent_session` on every event, plus a user ∩ agent intersection for delegated agents.

| Option | What the event records | Trade-off |
|---|---|---|
| **Hook as its own principal** | `actor = hook:<id>@<version>`; permissions are the hook's own admin-granted scopes | Clean least privilege; history no longer shows which human started the chain unless causation is also stored |
| **Hook as the triggering user** | `actor = user`; permissions are the user's | Matches YouTrack and Salesforce in-transaction behavior; allows privilege laundering if the hook does things the user never chose; offline impersonation needs rules (Forge's `asUser()` limits) |
| **Triple attribution** | `principal` (whose permissions were checked), `on_behalf_of` (human or agent at the root), `originating_hook` + `causation_id` | Answers both "who could" and "why"; extends the agent attribution model already designed; costs three fields on every event and discipline in every caller |

The privilege question deserves its own decision. "Run as" any user, as in Jira's actor setting, is an escalation surface. Effective rights for a hook acting on behalf of someone could be the intersection of the hook's grant and the user's rights, mirroring the agent rule.

### Choice 4: how do hooks version with Type versions?

The earlier research split Type version behavior three ways: pin the lifecycle, upcast the schema, float the policy. Named code units carry their own semantic versions, with the Type pinning major versions. Hooks force a decision about which bucket they fall into.

| Option | Precedent | Fits | Risk |
|---|---|---|---|
| **Pin hooks with the lifecycle** (guards, validators and reactions are part of the immutable Type version) | Camunda listeners in the deployed BPMN (unverified); Appian process model versions (unverified) | Transition guards and post-transition reactions | A fix to a buggy validator doesn't reach in-flight Items without migration; listener-migration edge cases (Camunda #53122) |
| **Float hooks at latest** (resolved at run time) | Pega rule resolution (unverified) | Compliance validators that must apply to old Items now | In-flight Items change behavior under users; harder to reason about |
| **Snapshot configuration, pin code by major version** | Camunda element templates copy values into the deployed version and pin job types like `io.camunda:http-json:1` (unverified); Kafka Connect plugin versions (unverified) | Connectors and reactions | Two version axes to manage (configuration schema and code) |
| **Classify per hook** (each hook declares `pin` or `float`) | None found | Mixed needs | Adds an authoring concept; needs a lint that flags floating hooks touching lifecycle fields |

Two further decisions follow. First, should a hook declare the fields it reads and writes, YouTrack `requirements` style, checked at Type publish? The earlier research already proposed this. Second, should migration run with hooks off by default? The earlier research said yes. The open question is whether certain validators, such as compliance checks, must instead run against the migrated state.

### Choice 5: how are connectors packaged?

Across Camunda, Kafka Connect, Appian, n8n and Zapier (all **unverified**), connectors split into the same parts: code (a plugin or worker, versioned by type string), a declarative configuration template (schema plus UI), and secrets referenced by name and resolved only in the runtime. Camunda's `{{secrets.MY_KEY}}` is substituted by the Connector runtime, so the engine and process variables never hold the secret ([Camunda inbound connectors](https://docs.camunda.io/docs/components/connectors/use-connectors/inbound/), unverified). The Drift breach adds a fourth part, the **installation**: one scoped, short-lived, revocable credential per connector instance, with query auditing the connector's own principal cannot erase.

| Option | Shape | Gains | Costs |
|---|---|---|---|
| **A. First-party connectors only** | Kernel ships a fixed set (email, Slack, webhook, Git) as Temporal activities and outbox subscribers | Small attack surface; one quality bar | Customers build around the gaps with webhooks |
| **B. Template plus worker, Camunda style** | Versioned template (schema, UI, retries), versioned code identified by `name:major`, secrets by reference, configuration snapshotted into the Type version | Clean version axes; marketplace-ready | A connector runtime to operate; template-update UX |
| **C. Declarative components, Dapr style** | Named YAML components with `direction: input|output`, explicit ack and retry contract per component | Simple mental model; delivery guarantees documented per component | Less suited to rich UI configuration |
| **D. Kafka Connect style plugins** | Pluggable code with offsets, exactly-once sources, dead-letter queues | Proven for bulk data movement | Heavy; built for data pipelines, not work items |

Outbound delivery semantics are a decision in their own right. A **thin event plus re-fetch** (Notion signal-only payloads, unverified; Stripe "thin events," not verified) avoids leaking fields through payloads and plays well with the single projection function. A **full payload rendered by `Project`** saves a round-trip but freezes a view of the Item. Either way, the evidence favors exposing the outbox as a **durable, replayable cursor** (CDC style) with a stable event ID and per-Item sequence, and building push webhooks on top. Endpoints should auto-disable after sustained failure, with owner notice and replay from the cursor. Pushes that drop events during a circuit break, as Zendesk's do, should be avoided.

For inbound, the tentative rule (inbound connectors are just callers of the five operations) matches YouTrack and Salesforce, where API and import writes go through the same pipeline. Three refinements are open. The first is a typed `source` field (ui, api, import, email, connector, agent) that CEL and policy can branch on, as Salesforce varies validation by request source. The second is a privileged, audited bypass for bulk import, unlike ServiceNow's `setWorkflow(false)`, which any API caller can set. The third is a mandatory dedupe key per inbound message, like Camunda's message ID expression (unverified) and Zapier's dedupe on `id` (unverified).

### Choice 6: how do agents and connectors meet safely?

Agents appear on both sides of the extension model. They can be **hook targets**: a reaction that asks an agent to triage, draft or summarize. They can be **actors behind inbound connectors**: an MCP client calling the five operations. They might also become **hook authors**. The GitHub MCP and GitLost incidents share a "lethal trifecta" structure: private data, untrusted instructions arriving through event content, and an outbound channel. The earlier policy research already proposed tagging externally writable fields as untrusted and gating egress when the audience is wider than what the agent read.

| Option | Gains | Costs |
|---|---|---|
| **Agents only as post-commit reactions, with capabilities scoped to the triggering Item** (one Item per session, as Invariant recommends one repo per session) | Shrinks the private-data side of the trifecta | Cross-Item tasks such as "find duplicates" need explicit, audited widening |
| **Agent outputs to external channels go through a separate, policy-checked step** (a propose state or an approval) | Breaks the egress side; GitLost's researchers recommend human review before publishing | Latency; risk of approval fatigue ("Always Allow") |
| **Provenance tags on event payload text** (author kind and trust level carried through the outbox and connectors) | Lets agent context assembly and CEL distinguish customer-written text | Every connector must preserve tags; text pasted between fields launders provenance |
| **Agent-authored hooks never self-publish** (drafts only, human publish, dry run against live Items) | Covers the theoretical authoring risk cheaply | Slows agent-driven configuration |

Detection-based defenses are weak. GitLost bypassed threat detection with one word. Structural limits on scope, egress and publishing are the parts that hold.

## Candidate names for the kernel's extension points

The naming goals follow from the collisions above. Each name should say when it runs. It should avoid "trigger" and bare "listener," and reserve "worker" for one meaning. It should keep the distinction between "returns a decision" and "causes effects" visible in the word itself. Three naming families are worth brainstorming.

| Extension point | Family 1: tracker-familiar | Family 2: admission-style | Family 3: plain lifecycle verbs | Notes |
|---|---|---|---|---|
| Transition or action offered at all (pure, pre-write) | Condition | Guard | `allow_if` | "Guard" matches YouTrack and statechart usage and already appears in the Type draft |
| Write rejected with a message (CEL, in txn) | Validator | Admit / Check | `require` | Jira users know "validator"; K8s users know "admission" |
| Field derived or corrected before write (CEL, in txn) | Computed field | Mutate / Derive | `set` | Keep separate from validation so authors know which can change data |
| Remote allow, deny or correct (pending state) | External validator | Review / External check | `hold_for` | If modeled as an approval, "approval" may be the right word |
| Effect after commit (Temporal activity) | Post-function | Reaction | `then` / `on` | "Post-function" helps Jira migrants but implies synchronous timing it won't have |
| Outbound connector (event-stream subscriber) | Webhook / Integration | Feed / Sink | `notify` / Subscription | "Subscription" names the durable cursor model honestly |
| Inbound connector (caller of the five ops) | Integration / Intake | Source | `intake` | Kafka's source and sink pair is clear and widely understood |
| Time-based rule | Scheduled rule | Timer | `on_schedule` | Distinguish from SLA timers, which are already first-class |
| Platform interception (internal only) | Interceptor | Interceptor | Interceptor | Not customer-facing; matches Orleans and Temporal usage |
| Executor of reactions and connectors | Runner | Worker | Runner | "Worker" collides with Kafka Connect's host process and Temporal workers |

A mixed vocabulary is defensible: **guard, check, derive, review, reaction, subscription, source, schedule**, with "hook" as the umbrella term in documentation only. It keeps one word per timing position, and none of the words carries a conflicting meaning in a major neighbor product. Jira migrants would need a mapping table (condition → guard, validator → check, post-function → reaction), which the Jira import report could generate automatically.

## Conclusion

The research reframes the tentative rule as a ladder rather than a wall. The kernel does not have to choose between "only CEL" and "arbitrary code in the transaction." The industry's working answer is pure, metered logic inside the commit, plus a narrow, explicitly fail-open-or-closed escape hatch that never holds the transaction open. Kubernetes, Shopify and (reportedly) Camunda 8 all landed there. The kernel's distinctive opportunity is that its escape hatch can reuse machinery it already needs. A blocking remote check is an approval completed by a machine, under the same pending state, SLA, audit and Temporal wait that human and agent approvals use.

The second opportunity is one no surveyed platform has taken: **causation lineage as a first-class field**. Every vendor detects loops by counting, and every vendor's audit trail loses the "why." The same `causation_id`, hop count and originating-hook fields would serve loop prevention, the user-facing "why did this fire" trace, agent attribution and injection forensics at once. That is a cheap decision now and an expensive retrofit later, and it is a point of differentiation rather than catch-up. The biggest remaining uncertainty is evidentiary. The BPM, low-code and most actor-runtime details are unverified prior knowledge, so a short verification pass on Camunda 8 listener semantics and Shopify's checkout failure behavior should come before either becomes a load-bearing precedent.
