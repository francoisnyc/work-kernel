# Design search into the kernel early

Search stays fast at scale when the data model guarantees four things. Every query hits one tenant partition. Permissions show up in the index as a small number of precomputed scope IDs, not as rules worked out per hit. Per-tenant schema is capped and mapped onto fixed typed slots. The API refuses unbounded work: deep offsets, exact totals, empty queries and fat payloads. Jira got slow because it broke each of these. Permission and issue-security checks grew with projects, schemes and security levels. JQL functions expanded to about 100,000 IDs before the engine saw them. Sorting ranked every match to return 50 rows. Custom fields grew without limit. Atlassian has spent 2024–2026 undoing this. It rebuilt the Cloud search API around cursors, approximate counts and explicit read-your-writes reconciliation, moved Data Center off per-node Lucene, and began enforcing per-space caps on fields and security levels. Slack, Linear, Notion, Discord and GitHub all converge on the same shape: tenant-partitioned indexes, a cheap first-stage retrieval followed by an application-layer rerank or permission check, and an asynchronous indexer fed by a durable log. Your kernel already has the hard parts. The single-container rule with narrow-only inheritance makes permissions compress unusually well, and the event log is a ready-made indexing feed. The recommendations at the end turn these lessons into schema, policy, tenancy, freshness and API constraints, with numeric targets.

## Jira slowed down because permissions, configuration and the API were unbounded

In Jira Data Center, JQL compiles to a query against a **Lucene index kept locally on each node**. Nodes sync by polling a database operation log **every 5 seconds**, so they are only eventually consistent with each other ([Atlassian](https://confluence.atlassian.com/enterprise/jira-data-center-search-indexing-939499986.html)). Atlassian's own breakdown of JQL cost puts **permission checking** first. Every search must work out which projects the user can browse and which issues issue-security hides from them, and that cost grows with permission schemes, projects and security schemes. When the query names a project, Jira narrows the permission work, so `project = X AND summary ~ y` can beat `summary ~ y` ([Atlassian KB](https://support.atlassian.com/jira/kb/factors-contributing-to-jql-performance-in-jira-server-and-data-center/)). The worst case is documented. With **more than 20 security levels** and many groups, an "Assigned to me" gadget took **over 10 seconds on only 40,000 issues**, and the ticket closed with no fix version ([JRASERVER-31288](https://jira.atlassian.com/browse/JRASERVER-31288)).

The other costs come from expressiveness that sits outside the planner. JQL functions run before the search, like macros. Atlassian's example returns **about 100,000 issue IDs** that are ANDed into the Lucene query, ignoring the other clauses. Sorting forces every match to be ranked to fill a 50-row page. `filter IN (1,2,3,4)` runs five complete searches ([Atlassian KB](https://confluence.atlassian.com/jirakb/understanding-jql-performance-740263450.html)). Configuration bloat compounds all of this. Atlassian rates under **800 custom fields** as optimal and over 1,200 as exceeding the limit, with slower JQL and longer reindexes as the cost ([Atlassian](https://confluence.atlassian.com/enterprise/managing-number-of-custom-fields-in-jira-data-center-1488597907.html)). Its guardrails also flag 1,000 comments and 20,000 change-history items per issue ([Jira guardrails](https://confluence.atlassian.com/adminjiraserver/jira-software-guardrails-1141488685.html)). One community case cut a full reindex from **8 h 10 min to 35 min**. Part of the gain came from scoping 40 global-context custom fields, which shrank the index by 22% ([Atlassian Community](https://community.atlassian.com/forums/Data-Center-articles/Data-Center-Admins-How-We-Cut-Jira-Reindex-Time-from-8-Hours-to/bc-p/3253535)).

Atlassian's fixes fall into three moves. First, in 2021 Jira Cloud ran on per-tenant Postgres, and one JQL query compiled to **about 100 lines of SQL joining 26 tables** ([Atlassian Engineering](https://atlassian.com/blog/atlassian-engineering/reducing-jql-database-load-with-caches/amp)). Atlassian added a two-stage cache. Stage 1 is a candidate set computed without permissions, shared across users and invalidated by events. Stage 2 applies per-user permissions and sorting with a 5 s TTL. That cut **database load per user by 76.6%**. Second, Atlassian moved Cloud JQL to a new eventually consistent engine and redesigned the API around it ([RFC-61](https://community.developer.atlassian.com/t/rfc-61-evolving-search-capabilities-addressing-scalability-with-a-new-enhanced-search-api/83027)):

| Old feature | Replaced by | Reason |
|---|---|---|
| Offset pagination | Cursor (`nextPageToken`) | Returning row 10,000 meant filtering and ordering the 10,000 before it |
| Exact `total` | Separate approximate-count endpoint | Counting on every page hurt large searches |
| Full issue payloads | Only `id` by default, plus a bulk-fetch endpoint | Payloads caused out-of-memory errors |
| Empty or ORDER BY-only JQL | Returns HTTP 400 | Unbounded scans |

Atlassian claims **99% of queries finish under 500 ms, versus 94% before**. Reads are eventually consistent, with lag of "seconds to minutes". Callers get read-your-writes for **up to 50 issue IDs** through `reconcileIssues` ([Atlassian docs](https://developer.atlassian.com/cloud/jira/platform/search-and-reconcile/)). Third, in 2026 Atlassian turned advisory guardrails into enforced caps: **700 fields and 150 work types per space**, and from September **50 security levels per space** and **50 grants per permission** ([Atlassian Support](https://support.atlassian.com/jira-cloud-administration/docs/data-limits-and-guardrails/)). Atlassian says outright that fewer fields "reduce index size, search complexity" ([Atlassian blog](https://www.atlassian.com/blog/how-we-build/optimisation-tools-for-jira)). Data Center is following. It now has an OpenSearch backend with a **10,000-result window cap** and read-your-writes as the default consistency mode ([Atlassian](https://confluence.atlassian.com/adminjiraserver/configuring-opensearch-for-jira-1620511851.html)).

The lesson is that every one of these limits could have been designed in on day one. Atlassian added them only after customers depended on the unbounded behavior. Atlassian has not published the internals of the new Cloud engine, so it is unknown whether permissions are applied as pre-filters or post-filters there.

## Fast peers partition by tenant and push expensive work out of the engine

Every peer with public engineering detail routes a query to a single tenant partition and keeps those partitions bounded in size.

| Product | Engine | Partitioning | Freshness | Published performance |
|---|---|---|---|---|
| Slack | Solr; application-layer re-rank on social and "work graph" features | Index built separately per EKM customer; general shard layout not published | Lambda architecture (batch plus stream) | Re-rank raised clicks at position 1 by 27% ([Slack](https://slack.engineering/search-at-slack/)) |
| Linear | turbopuffer (replaced Elasticsearch and pgvector in 2025); hybrid BM25 plus vector, rank fusion, Cohere rerank | Namespace per (org, table); 4M+ namespaces | Postgres to turbopuffer replication about 1 s p50, a few seconds p95 | 13 ms p50 search, 70% cost cut (vendor-reported) ([turbopuffer](https://turbopuffer.com/customers/linear); [Linear](https://linear.app/now/rebuilding-delta-sync-read-path)) |
| Notion | Elasticsearch (lexical); turbopuffer (vector) | Workspace assigned to an index, routed by `spaceId`; namespace per workspace for vectors | Kafka online path keeps live workspaces fresh within a minute; Spark offline reindex | Vector p50 down from 70–100 ms to 50–70 ms, 60% lower spend ([Notion](https://www.notion.com/es/blog/two-years-of-vector-search-at-notion); [Notion](https://www.notion.com/blog/rebuilding-notions-lexical-search-reindexer)) |
| Discord | Elasticsearch "cells" of many small clusters | By guild; DMs stored under each participant; huge guilds moved to dedicated multi-shard indexes; target about 200M messages / 50 GB per index | Lazy, queue-fed bulk indexing | Median under 100 ms (from 500 ms), p99 under 500 ms (from 1 s), trillions of messages ([Discord](https://discord.com/blog/how-discord-indexes-trillions-of-messages)) |
| GitHub Issues | Elasticsearch, with a new PEG-parser-to-AST query layer | Not published | Not published | About 2,000 QPS (160M queries/day); nesting capped at 5 levels ([GitHub](https://github.blog/developer-skills/application-development/github-issues-search-now-supports-nested-queries-and-boolean-operators-heres-how-we-rebuilt-it/)) |

Three patterns recur. The first is **two-stage retrieval**. The engine does cheap candidate generation. Slack's Solr sort uses only a few easy features. Then the application layer does the expensive rerank or the exact permission check. GitHub code search applies permissions both ways. It rewrites the query to cover accessible repo IDs, then filters again after the merge using Redis-cached ACLs ([GitHub](https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/)).

The second is **one permission path for humans and AI**. Slack AI runs as the requesting user and reuses the standard search and fetch libraries, so it "never surfaces results standard search wouldn't" ([Slack](https://slack.engineering/how-we-built-slack-ai-to-be-secure-and-private/)).

The third is **denormalizing to avoid permission joins**. Discord writes each DM under both participants, doubling storage so that a cross-DM search needs no join. Notion stores permissions on every vector chunk. When only permissions change, it patches metadata instead of re-embedding ([Notion](https://www.notion.com/es/blog/two-years-of-vector-search-at-notion)).

Linear's case teaches one more thing. Being local-first did not remove server search. Workspace-wide full-text and semantic search is a server call to a per-tenant index. Linear also reuses the same per-attribute posting lists for its permission-aware sync read path. On Postgres, p95 latency for that path grew with workspace size. On turbopuffer it stays roughly flat.

## Containment-inherited permissions compress into scope IDs, if the kernel keeps them bounded

Every source that compares the options prefers **pre-filtering**: principals or scopes are stored in the index and the filter runs inside the engine. Post-filtering only works when users can see most of the candidates. When visibility is sparse, pages come back short or empty and paging has to loop. In vector search, post-filtering can return **0% recall**, while exhaustive pre-filtering takes 10 s. Filter-aware engines target ≥90% recall at about 25 ms ([turbopuffer](https://turbopuffer.com/blog/native-filtering)). AuthZed's guidance gives the practical rule. Fetch the user's accessible IDs and filter on them when that set is **under about 10,000**. Bulk-check candidates after a selective query when it is larger. Materialize permission sets into the index when both approaches are prohibitive ([AuthZed](https://authzed.com/docs/spicedb/modeling/protecting-a-list-endpoint)).

There are two different kinds of fan-out, and each needs its own fix. **Inheritance fan-out** happens when effective ACLs are copied onto every descendant. In Confluence, changing a page restriction forces a reindex of all child pages, comments and attachments ([Atlassian KB](https://support.atlassian.com/confluence/kb/page-restrictions-performance-considerations/)). SharePoint avoids copying by having items inherit a *scope*, but its query-time effective limit can fall to **1,000–2,000 scopes** ([Microsoft](https://learn.microsoft.com/en-us/sharepoint/sites/best-practices-for-using-fine-grained-permissions-in-sharepoint-server)). **Group fan-out** happens when groups are expanded into user lists. Glean and Microsoft's own RAG guidance both say to store group IDs on documents and expand the user's groups at query time, because flattened membership goes stale ([Glean](https://developers.glean.com/libraries/indexing-sdk/permissions); [Microsoft ISE](https://devblogs.microsoft.com/ise/sharepoint-doc-level-access/)). Zanzibar's Leopard index flattens nested groups into user→groups and group→descendant-groups sets for exactly this lookup ([Zanzibar](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)).

Your containment rule makes this simpler. The following is analysis, not something a source states. Each item has at most one container, and a child can only narrow its container's policy. So the set of users who can read an item is the reader set of its **nearest ancestor-or-self that narrows read policy**. Call that item's *policy scope*. Each scope's reader set is a subset of its parent scope's reader set. The index therefore needs one `scope_id` per item document. A user's visibility is a set of scope IDs. Changing an ancestor's policy rewrites only scope→reader records, not descendant documents. Only two kinds of write touch documents. Moving an item to a new container re-points the subtree, and adding or removing a narrowing policy on an item re-points every descendant whose nearest scope changes. Both are bounded by subtree size.

The remaining risk is a user who can see a very large number of scopes. Chat makes this concrete, because every private channel and DM is a scope. Treat **tenant-wide-readable scopes** as a single flag. The filter then becomes `tenant_readable OR scope_id IN user_private_scopes`, and the terms list holds only the user's private scopes. Jira's cap of 50 security levels per space and AuthZed's ~10,000 threshold both indicate that this list has to stay bounded.

Index-based permissions are always stale for some window: about 15 minutes by default in SharePoint, and "next indexer run" in Azure AI Search ([Microsoft](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)). Pair the pre-filter with an **exact policy check on the final top-k (10–50 hits)** against the kernel's live policy. Revocations then take effect on returned results immediately, even while the index catches up. This is the same pre-filter-plus-post-filter split GitHub uses.

**Field-level security** maps poorly onto engine features. Elasticsearch's document- and field-level security is configured per role, not per document. Its aggregations can still leak counts and terms from restricted documents, and global term statistics include hidden documents ([Elastic](https://docs-v3-preview.elastic.dev/elastic/docs-content/pull/8094/deploy-manage/security/limitations.md)). Search Guard rates document-level security as a "Medium-High" cost and sets a target of **p99 under 100 ms with it versus 50 ms without** ([Search Guard](https://docs.search-guard.com/latest/performance-tuning)). The safer pattern is to put restricted field values in a **separate sub-document carrying its own narrower scope_id**. Those values must never enter shared full-text fields, snippets or embeddings. Otherwise a match on a hidden field returns the parent and reveals that the hidden value matched. For the same reason, facets and counts must be computed after trimming.

## Engine choice matters less than the document contract, but Postgres runs out on ranking and vectors

| Option | Strengths | Limits | Fit |
|---|---|---|---|
| Native Postgres FTS (tsvector/GIN) on the read model | Transactional read-your-writes; no extra system | No top-k pruning: on common terms, **115 QPS / 109 ms p50 vs 3,373 QPS / 1.4 ms** for a BM25 extension; no BM25 ([ParadeDB, vendor benchmark](https://paradedb.com/blog/benchmarker-iteration)) | Structured filters, ID and title lookups, rare terms |
| Postgres BM25 extensions (ParadeDB, pg_textsearch, VectorChord-BM25) | BM25 with block-max WAND; stays in-transaction | Write and merge cost on OLTP not benchmarked, by ParadeDB's own admission | Early-stage full-text without a second store |
| pgvector 0.8+ | Same database; iterative scans fix short filtered results | Scans capped at 20,000 tuples by default; HNSW about **20–25 KB per 1536-d vector**; strain at ~10M, rethink at ~100M ([ClickHouse](https://clickhouse.com/resources/engineering/scale-vector-search-postgres); [PostgreSQL.org](https://www.postgresql.org/about/news/pgvector-0.8.0-released-2952/)) | Small tenants; exact scans of a tenant's subset |
| Elasticsearch / OpenSearch | Mature; native RRF hybrid; routing and filtered aliases | **1,000-field default cap**, 100k "strong performance implications" ([Elastic](https://www.elastic.co/docs/troubleshoot/elasticsearch/mapping-explosion)); per-index overhead under index-per-tenant | Pool small tenants by `_routing=tenant`; silo large ones ([BigData Boutique](https://bigdataboutique.com/blog/multi-tenancy-with-elasticsearch-and-opensearch-c1047b)) |
| turbopuffer | Namespace per tenant (unlimited namespaces); BM25 plus vector plus filters; $0.33/GB storage | Commercial only; up to 200 ms write commit; cold p999 in the hundreds of ms; **16 concurrent queries per unpinned namespace**; 1,024 attributes per namespace ([turbopuffer](https://turbopuffer.com/docs/tradeoffs); [limits](https://turbopuffer.com/docs/limits)) | Linear and Notion's choice for tenant-partitioned hybrid search |
| Vespa streaming mode | About 45 bytes RAM per document; each query scans one group | Exact nearest neighbor only (no HNSW) ([Vespa](https://docs.vespa.ai/en/streaming-search.html)) | Per-tenant or per-user chat archives |
| Typesense / Meilisearch | Simple; scoped keys and tenant tokens | Typesense holds indexed fields in RAM; Meilisearch has a single write leader ([Typesense, vendor comparison](https://typesense.org/typesense-vs-meilisearch/)) | Small and medium corpora |

**Freshness** depends on the indexing path. Debezium polls every 500 ms by default, Kafka batching adds about 20 ms, and Elasticsearch refreshes every 1 s (5 s on Serverless), with `refresh=wait_for` available to block a write until it is visible ([RisingWave](https://risingwave.com/blog/debezium-performance-tuning-throughput-latency/); [Netdata](https://www.netdata.cloud/guides/elasticsearch/elasticsearch-refresh-interval-tuning/)). Adding up those defaults gives an estimated **p50 of 1–2 s and a p99 of several seconds** under load. No production blog in the notes publishes a measured end-to-end distribution. Linear's roughly 1 s p50 replication is the closest real figure.

The kernel's event log can feed the indexer directly, which avoids WAL decoding. The indexer must be idempotent and ordered by item version, as Notion does with `version_type: external`. Read-your-writes then needs an explicit mechanism. Jira's `reconcileIssues` is one model. A stronger general pattern is a **commit sequence token**: the write returns the event-log sequence, and search compares it with the indexer's applied watermark. If the indexer is behind, search waits briefly, then overlays the session's recent writes from the Postgres read model by ID.

**Agents** change the load profile more than they change the architecture. The notes found **no published data on agent versus human query volume inside SaaS search**, so any multiplier is an assumption. Web-wide, automated traffic grew about 8x faster than human traffic in 2025 ([Implicator / HUMAN Security](https://www.implicator.ai/human-security-reports-ai-traffic-surged-187-in-2025-as-bots-eclipsed-human-users/)). Agent queries are mostly structured filters, run in parallel bursts, and are followed by bulk hydration. They also need read-your-writes more than humans do: an agent that creates an item and cannot find it will create it again.

Hybrid search is now table stakes. Linear rebuilt its search as semantic plus keyword ([Linear](https://linear.app/changelog/2025-04-10-new-search)). **Reciprocal rank fusion (k=60, window 50–100)** needs no tuning and costs only about 4% NDCG against tuned fusion ([BigData Boutique](https://bigdataboutique.com/blog/reciprocal-rank-fusion-how-it-works-and-when-to-use-it)). Agents must retrieve as the end user, never as a broad service account, as Slack AI and Glean do. Derived artifacts such as summaries and cached embeddings must carry the **intersection** of their sources' scopes.

## Design constraints and recommendations for the kernel

### What must be indexable

| Element | Index as | Rule |
|---|---|---|
| Item core | `tenant_id`, `item_id`, `type`, `state`, `container_id`, `scope_id`, `tenant_readable`, `created_at`, `updated_at`, `version`, author/assignee principals | Fixed schema across all Types |
| Text | Title and body as separate fields; per-language analysis if multilingual (Slack uses per-locale fields) | Bodies capped (Jira degrades past 100k characters for multi-line text) |
| Custom fields | Typed slots `kw_1..N`, `num_1..N`, `date_1..N`, `text_1..N` through a per-tenant, per-Type registry; overflow fields go to filter-only key/value storage | Each field declares one of `filter`, `sort`, `text` or `none`; only declared fields are indexed |
| Links | Keyword array `link_type:target_id` | Cap links per item (Jira guardrail: 1,000) |
| Containment | `container_id` plus a bounded ancestor path for "everything under X" queries | Cap containment depth |
| Messages and comments | Each is its own Item document in its container's scope | Never concatenate children into the parent document |
| History | Not in the main index. Index only derived facets ("state changed at", "last actor"); serve full history from Postgres or the event log by item_id | Jira guardrail: 20,000 change items per issue |
| Restricted fields | Separate sub-document with its own narrower `scope_id` | Never copied into shared text, snippets or embeddings |
| Embeddings | Chunk-level, carrying the source's `scope_id`; metadata patched (not re-embedded) on policy change | Derived content takes the intersection of its sources' scopes |

### How policy and containment must be represented

The kernel should keep a `scope` table holding each item that defines a narrowing policy, its parent scope, and its resolved reader principals (users and groups). It should also keep a Leopard-style user→groups expansion. At query time, it resolves `{user, groups}` to a set of visible private scopes, caches it with a short TTL, and passes it as a terms filter alongside `tenant_readable`. Policy edits on an ancestor update scope records only. Moves and the creation or removal of narrowing policies trigger an asynchronous subtree re-point. Every response's top-k is checked exactly against live policy, which closes the revocation window. When a user's visible private scopes exceed about 10,000, switch to a selective-query-then-bulk-check plan. Product limits should keep that case rare.

Field policies should be declared on the Type's field definition rather than set ad hoc on each instance. That keeps the number of distinct field scopes small enough to precompute. Facets, counts and "about N results" must be computed after the permission filter, never before.

### Tenancy and sharding

Every query carries `tenant_id` as a mandatory predicate, and every partition belongs to one tenant. Pool small tenants in shared indexes routed by tenant, or use one namespace each on a namespace-native engine. Promote large tenants, and Discord-style "huge guilds", to dedicated partitions sized to stay around **10–50 GB or about 200M documents per shard/index**. Chat and tracker items can share one document contract. Splitting them into separate partitions per tenant (as Linear keys namespaces by (org, table)) lets the high-volume chat corpus scale independently. Cross-tenant admin search is a separate system.

### Phasing the engine

The following is a recommendation built from the evidence above. Start with structured filters on the Postgres read model, since that gives read-your-writes for free, and add a BM25 extension plus pgvector for text and semantic search. Define the index document contract and the event-log indexer from day one, so the engine can be swapped. Plan to move full-text and vector search to a tenant-partitioned engine (turbopuffer, or OpenSearch/Elasticsearch with routing) when common-term latency, write contention on the OLTP database, or vector counts near 10M per instance show up. That is the move Linear made from Elasticsearch plus pgvector.

### Freshness and read-your-writes

Every kernel write returns `commit_seq`, the event-log position. Search accepts `min_seq`. If the indexer watermark is at or past `min_seq`, the query runs normally. Otherwise search waits up to about 500 ms. If the watermark is still behind, it overlays items the caller changed since the watermark, fetched from Postgres by ID, then re-filters and deduplicates by version. Queries scoped to one item, one container's last N minutes, or pure structured filters can go straight to Postgres.

### API shape for humans and agents

One search endpoint should accept typed filters, optional `text`, a `mode` (`keyword`, `semantic` or `hybrid`), `sort`, `cursor`, `limit`, `min_seq` and `fields`. By default it returns IDs plus compact snippets. A separate bulk-fetch endpoint hydrates items. Totals come only from an approximate-count endpoint. Queries without a bounding filter or text are rejected. Boolean nesting is capped. Agents get the same endpoint exposed as MCP tools (`search` and `fetch`), run as the end user (or the intersection of agent and user permissions), have separate per-principal-type quotas, and get session-level query caching. Results the user can't see come back as an empty list, not a 403.

### Numeric targets

| Target | Value | Basis |
|---|---|---|
| Search latency, human interactive | p50 ≤ 100 ms, p99 ≤ 500 ms | Discord after re-architecture; Jira's 99% < 500 ms claim |
| Search latency, filter-only / agent structured | p50 ≤ 50 ms, p99 ≤ 100 ms including permission filter | Search Guard targets; Linear 13 ms p50 (vendor-reported) |
| Index lag (write to searchable) | p50 ≤ 1–2 s, p99 ≤ 5 s; alert at 60 s | Linear about 1 s p50; ES 1 s refresh; Notion under 1 min |
| Read-your-writes | 100% for the writer's own session through `min_seq`; wait ≤ 500 ms before overlay | Jira `reconcileIssues` (≤ 50 IDs) |
| Revocation effect on results | Immediate, via exact check of top 10–50 | AuthZed bulk-check pattern; GitHub post-merge filter |
| Visible private scopes per user | Design for ≤ 10,000 | AuthZed threshold |
| Narrowing policies (security-level analogue) per container root | ≤ 50 | Jira Cloud 2026 cap |
| Indexed custom fields | ≤ 200 per Type; ≤ 700 per space; ≤ 1,000 slots per index or namespace | Jira 700/space; ES 1,000 default; turbopuffer 1,024 |
| Options per select field | ≤ 20,000 | Jira Cloud 2026 cap |
| Page size | Default 50, max 100 hydrated / 1,000 ID-only | Jira "typically 100–5000"; bounded payloads |
| Result window | ≤ 10,000 per query via cursor | Jira OpenSearch cap |
| Boolean nesting depth | ≤ 5 | GitHub Issues |
| Partition size | ≤ 50 GB / ~200M docs before splitting | Discord |
| Hybrid fusion | RRF k=60, window 50–100; vector recall@10 ≥ 90% under ACL filters | RRF literature; turbopuffer |
| pgvector ceiling | Move off at ~10M vectors per instance or if p99 targets break | ClickHouse scale bands |

## Conclusion

The biggest choice here is not the search engine. It is the permission algebra. Narrow-only, single-container inheritance lets one `scope_id` per document stand in for arbitrarily deep policy, and lets ancestor policy edits skip reindexing entirely. Atlassian could not get that from Jira's mix of permission schemes and security levels, and Confluence pays for its lack in subtree reindexes. Protect this property. Any future feature that lets a child widen access, or lets an item sit in two containers, breaks the compression and brings Jira's cost curve back. Treat such features as search-architecture decisions, not product tweaks.

The second insight is that the kernel's event log and commit sequence already provide what Atlassian had to retrofit: an ordered, idempotent feed for the indexer and a natural read-your-writes token. Expose `commit_seq` from day one, before agents start writing and searching in tight loops. The open risk is agent query volume. No vendor has published how much agents multiply search load inside a SaaS product, so the per-principal quotas and usage metering above should be in place from the start, while that number is still unknown.
