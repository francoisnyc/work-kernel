# Scope table holds; guard every exit path

The Item kernel's Step A design is on solid ground where it matters most, and the risk sits in the paths around it. Every system studied either computes inherited access at read time (Zanzibar, OpenFGA, Notion, Jira) or precomputes it somewhere other than its source of truth (Confluence's search index, Notion's data lake, SpiceDB's paid Materialize add-on). For large list and search queries, the vendors push customers toward the end state the kernel already has: a precomputed permission set joined locally in the application's own database. A `scope_access` table updated in the same Postgres transaction as each policy change gives immediate revocation on primary reads without consistency tokens, which is stronger than the default in Zanzibar, SpiceDB or any document product studied. Narrowing a scope in place avoids the costs that led Confluence to reindex whole subtrees, SharePoint to cap inheritance changes at 100,000 items, Dropbox to refuse narrowing on folders with 100 or more members, and Box to forbid narrowing altogether. The documented leaks come from elsewhere: move notes, notification emails, search aggregates, attachments the index failed to update, asynchronous indexes, and agents that read under one audience and write to a wider one. The kernel has four structural exposures. Output paths can bypass the join. Async consumers will reopen the "new enemy" window. Lazy per-container scope nodes may multiply `scope_access` rows on a large narrowing. And moves, groups and sharing have no defined policy semantics yet. The cheapest fixes belong in Step A: one visibility function for every output path, moves treated as policy changes, sharing as additive grants rather than new scopes, a `principal` column that can hold groups from the start, a hidden-by-default rule for narrowed children, and property tests against a naive evaluator. Replica LSN checks, read-time rechecks for the external index, the group closure table, reconciliation jobs and full agent information-flow rules belong under "Later". Each has a defined hook in Step A so it can be added without a migration.

## Systems split on where inheritance is resolved, and nobody precomputes it in the core

The systems fall into three camps. **Zanzibar keeps tuples normalized and evaluates inheritance at check time**: a `tuple_to_userset` rewrite rule says, in the paper's example, "look up the parent folder of the document and inherit its viewers" ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). Its one denormalization is **Leopard**, which flattens nested *group* membership into GROUP2GROUP and MEMBER2GROUP sets and answers membership by set intersection. Even that costs a lot: one tuple change "may yield potentially tens of thousands of discrete Leopard tuple events" ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). Notion also resolves at read time. "A block's permission isn't statically stored," and each check walks ancestors "all the way up to the root," at depths "from a few to dozens." Bulk consumers (Search, AI) forced Notion to build a separate Spark pipeline that denormalizes permissions per block, because the same computation "would simply time out in Snowflake" ([Notion data lake](https://www.notion.com/blog/building-and-scaling-notions-data-lake)). Jira computes Browse projects and issue security levels per query, and Atlassian names that as the main search cost ([Atlassian KB](https://support.atlassian.com/jira/kb/factors-contributing-to-jql-performance-in-jira-server-and-data-center/)).

The second camp **stores one ACL per scope and lets items inherit by reference**. SharePoint is the clearest case and the closest structural match to the kernel: "If two files have the equivalent ACL because they both inherit from the parent folder, then they share an ACL. Only the parent folder counts" ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/manage-permission-scope)). The third camp **copies effective permissions onto every document**. Confluence stores permissions "on every item in the index" ([Atlassian KB](https://support.atlassian.com/confluence/kb/page-restrictions-performance-considerations/)), and Glean, Microsoft Graph connectors and Elastic's DLS-enabled connectors index ACLs with the content ([Glean](https://developers.glean.com/libraries/indexing-sdk/permissions); [Microsoft Learn](https://learn.microsoft.com/en-us/graph/connecting-external-content-manage-items)).

Two patterns stand out. First, **the published hard caps all guard against synchronous work proportional to subtree size or member count**: SharePoint's 100,000-item limit, Dropbox's 100-member limit, Confluence's reindex storms and Box's refusal to narrow at all. SharePoint adds that ACL size matters as much as scope count, since with "larger ACLs (up to 5,000 ACEs)" problems appear before the scope limit ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/manage-permission-scope)). Second, **the "list everything I can see" problem pushes everyone toward a local join**. AuthZed calls Materialize the option with "the greatest scalability," letting apps "sort, filter, and paginate over many thousands of authorized objects natively in your own database" ([AuthZed](https://authzed.com/docs/authzed/concepts/authzed-materialize)). Oso's local mode compiles policy into SQL against the application's tables ([Oso](https://www.osohq.com/docs/authorization-data/local-authorization)). Zanzibar never offered a list API at all. The kernel starts where these vendors end up, which confirms the earlier decision against SpiceDB and OpenFGA.

## The evidence backs the core design on five counts

**Single container.** Notion moved to one upward parent pointer because "ambiguity is unacceptable in a permissions system" ([Notion](https://www.notion.com/blog/data-model-behind-notion)). Google Drive gave every item "exactly one location" in 2020 ([Google](https://workspace.google.com/blog/product-announcements/simplifying-google-drives-folder-structure-and-sharing-models)). Both products moved *away from* multi-parent trees to get unambiguous inheritance.

**Scope-level ACL with items referencing it.** SharePoint's permission-scope model shows that inheritance by reference is how a large document system stores ACLs. Narrowing in place goes one step further than SharePoint: the scope keeps its ID, so no item row changes. That avoids Confluence's O(subtree) reindex, where Lucene's inability to update a record in place forces attachment content to be reindexed too ([Atlassian KB](https://support.atlassian.com/confluence/kb/page-restrictions-performance-considerations/)).

**Same-transaction maintenance beats tokens.** Zanzibar's two "new enemy" examples are a revoke followed by a move into the folder, and a revoke followed by new content ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). The kernel handles both by construction on the primary, because the scope row, the item row and the check share one MVCC snapshot. Zanzibar pays for freshness: Recent checks run at **60 ms p95 against 9.46 ms for Safe**, and Safe checks outnumber Recent by about two orders of magnitude ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). OpenFGA tells users of a `/changes`-fed index to `/check` every result, because revocations may not have reached the index yet ([OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)). The kernel's join does not need that recheck while it runs in the same store.

**Groups as IDs, not expanded.** Microsoft says to "avoid expanding the membership of your external groups directly into the ACLs of individual items because each group membership can lead to a high volume of item updates" ([Microsoft Learn](https://learn.microsoft.com/en-us/graph/connecting-external-content-manage-items)). Glean gives the same advice because flattened membership "changes constantly" ([Glean](https://developers.glean.com/libraries/indexing-sdk/permissions)). Leopard is the cautionary tale for flattening on the wrong side.

**User ∩ agent.** GitHub fine-grained tokens match this rule: "A token cannot grant additional access capabilities to a user," a token goes inactive when the user loses access, and organizations can require approval ([GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). ErrNotFound for hidden items also has precedent: AuthZed recommends an empty 200 rather than a 403 for filtered lists ([AuthZed](https://authzed.com/docs/spicedb/modeling/protecting-a-list-endpoint)).

## Exposure sits in exits, async consumers, row counts and undefined operations

### Output paths that skip the join are where the documented leaks happened

None of the incidents found involved a core ACL bypass on the main item view. In December 2019 a guest on a public GitLab project learned the name, issue count and creation date of a *private* project, because a confidential issue was moved there and the **move system note's HTML** exposed it through GraphQL ([GitLab #120026](https://gitlab.com/gitlab-org/gitlab/-/issues/120026)). Confluence warns that if attachments are not reindexed after a restriction, "users could see attachments they can't open in search results" ([Atlassian KB](https://support.atlassian.com/confluence/kb/page-restrictions-performance-considerations/)). Elastic says DLS "doesn't fully hide index contents": aggregations can reveal terms and counts from hidden documents ([Elastic](https://www.elastic.co/docs/deploy-manage/users-roles/cluster-or-deployment-auth/controlling-access-at-document-field-level)). Microsoft says pre-trimming "prevents information leakage for refiner data and hit count instances," while post-trimmed refiner counts can exceed visible results ([Microsoft Learn](https://learn.microsoft.com/sv-se/sharepoint/dev/general-development/custom-security-trimming-for-search-in-sharepoint-server)). Jira's notification path has a trail of tickets: secured-issue details in clear-text email (JRASERVER-37581), and watchers who kept receiving updates after their account was revoked (CVE-2021-39119). Both are **UNVERIFIED**, from ticket titles only ([JRASERVER-72737](https://jira.atlassian.com/browse/JRASERVER-72737)). Linear documents that personal API keys, team webhooks and Airbyte syncs can expose private-team data ([Linear](https://linear.app/docs/private-teams)). Figma's pre-DSL state shows the root cause: two codebases each implemented the rules, "discrepancies caused bugs," and "a bug in these functions could leak access to every single file in Figma" ([Figma](https://www.figma.com/blog/how-we-rolled-out-our-own-permissions-dsl-at-figma/)). The kernel's Get, write and search paths are correct, but counts, typeahead, snippets, notifications, webhooks, move notes, exports and agent retrieval are only correct if they go through the same function.

### Async consumers reopen the new-enemy window the transaction closed

The `min_seq` xid watermark gives read-your-writes on the primary. Postgres assigns sequence values before commit, so a cursor over IDs skips rows from slower transactions. The fix is to read only below `pg_snapshot_xmin(pg_current_snapshot())`, at the cost that one long transaction delays everyone ([event-driven.io](https://event-driven.io/en/ordering_in_postgres_outbox/)). That is why Watch and external indexes need the planned post-commit sequencer. Once they exist, the kernel inherits every index's freshness problem. Glean says webhooks "do not guarantee immediate permission updates" ([Glean](https://docs.glean.com/connectors/native/sharepoint/security/permissions)). Google says group membership transfers can take up to four days, during which "members might not see documents" ([Google](https://knowledge.workspace.google.com/admin/support/troubleshooting/membership-transfers-affect-access-to-groups)). Read replicas reopen the window in the same way, and SpiceDB's Postgres datastore exists partly to handle this: it checks whether a revision has reached the replica and falls back to the primary if not ([SpiceDB](https://authzed.com/docs/spicedb/concepts/datastores)). Hyperspell puts it plainly: "A stale permission cache is not a performance problem. It is a data leak" ([Hyperspell](https://www.hyperspell.com/blog/permission-aware-retrieval)).

### Lazy per-container scope nodes can multiply rows on one narrowing

The following is analysis of the kernel design, not a finding from any source. Every container gets its own scope node when its first child arrives. Most Items with comments or sub-items are therefore containers, so a large project can hold hundreds of thousands of scope nodes. Open scopes need no `scope_access` rows. When a project root is narrowed, though, every descendant scope stops being open and needs effective-reader rows. The recompute then writes **(descendant scope nodes) × (readers)** rows in one transaction, under top-down locks. That is Confluence's O(subtree) cost moved from the index into `scope_access`, and it is exactly the work SharePoint caps at 100,000 items. Unchanged descendant scopes all hold the *same* reader set, so the rows are pure duplication. SharePoint's own principle is that inheriting scopes share one ACL and "only the parent folder counts" ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/manage-permission-scope)). Storing groups as IDs keeps the reader factor small. It does not fix the scope-count factor.

### Moves, sharing and groups have no defined semantics yet

Moves change an Item's scope and therefore its readers, with no policy edit involved. Zanzibar's first new-enemy example is literally a move into a just-narrowed folder ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). Jira's rule is that a moved item adopts the target's default security level, and if the target has no scheme, "anyone with access to that space can see the item" ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/configure-issue-security-schemes/)). Drive requires share permission to move, and inherited access "is lost" while direct grants are kept ([Google](https://workspace.google.com/blog/product-announcements/simplifying-google-drives-folder-structure-and-sharing-models)). For sharing, SharePoint is the warning. "If you share a file or folder, this action breaks permission inheritance," each break adds a scope, and the system never cleans up, "because automatic restoration of the permission hierarchy isn't implemented due to security concerns" ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/manage-permission-scope)). Jira hits the same wall from the other side: more than 20 security levels on 40k issues made a gadget take over 10 seconds ([JRASERVER-31288](https://jira.atlassian.com/browse/JRASERVER-31288)), and Cloud now caps 50 levels per space ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/data-limits-and-guardrails/)). On groups, storing IDs moves the cost to query time and, once groups nest, brings back Zanzibar's "recursive pointer chasing" problem that Leopard exists to solve ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)).

### Agents legitimately read, then write to a wider audience

The two reference incidents were not ACL bypasses. In Slack AI (August 2024), an attacker's instruction in a public channel the attacker had created alone landed in the same context as the victim's private-channel secret. Slack AI then rendered a link carrying the secret to the attacker's server, and the citation pointed only at the victim's message. Slack initially called public-channel searchability "intended behavior" ([PromptArmor](https://promptarmor.com/resources/data-exfiltration-from-slack-ai-via-indirect-prompt-injection)). In the GitHub MCP case (May 2025), a malicious public issue hijacked an agent whose token covered all the user's repositories, with "Always Allow" on, and the agent leaked private-repo data into a public PR. Invariant Labs called it architectural and recommended one repository per session ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Microsoft's Copilot guidance adds the passive version: Copilot "utilizes all data that a user has access to, which may include broadly shared files that the user is unaware of" ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/sharepoint-copilot-best-practices)). User ∩ agent is necessary but does not stop any of these. The kernel's "approval to widen an audience" rule targets the right failure, but it needs a precise definition of *audience* that covers every way an agent can send data out.

## Recommendations ranked by value and cost

The table ranks each change by value (leak or outage prevented) against cost (engineering effort plus migration risk if deferred). The "Phase" column answers what to fold into Step A. The rule used was: fold in anything that fixes a schema shape, an API signature or an invariant that would be expensive to change once data exists, and defer anything that only matters when a consumer (replicas, external index, notifications, nested groups) exists.

### 1. One visibility function for every output path

Define `visible(principal, item_ids) → subset` and `visible_filter(principal) → SQL predicate` as the **only** ways any code path resolves Items for output. That covers Get, search hits, counts and "N results", facets, typeahead, snippets and highlights, related-item lists, notification recipients and bodies, webhook payloads, exports, link previews, move and system notes, and agent retrieval and tool results. Counts and facets are computed *after* the filter, never from an unfiltered set, following Microsoft's pre-trimming rule and Elastic's aggregation warning. Notification and webhook recipients are resolved at **send** time, not when the event is queued, which closes the Jira watcher class. Rendered references to other Items (for example "moved to X") pass the target through `visible` and redact the title when it fails, which closes the GitLab class. Enforce it the way Figma did: a single engine plus a test suite as the gate ([Figma](https://www.figma.com/blog/how-we-rolled-out-our-own-permissions-dsl-at-figma/)). Add a lint or test that fails when any query touches the items table outside the visibility module. It costs little now because Step A has few output paths. Retrofitting it later means auditing every serializer, which is what Jira refused to do for field security.

### 2. Moves are policy changes

A move goes through the same transaction, lock order, audit entry and event type as a narrowing. It needs write rights on both source and destination, as Drive requires share rights. It is decided by comparing reader sets. Because inheritance only narrows, a move to the source scope or one of its descendants can never widen access. Any other destination does widen if the destination's reader set has principals the source lacks, and a widening move needs explicit confirmation showing "+N people", or is blocked from narrowed to open scopes unless an admin overrides. GitHub's conservative rule is the precedent: a private-repo issue cannot move to a public repo ([GitHub Docs](https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/transferring-an-issue-to-another-repository)). A moved Item that is itself a container keeps its scope node, so only its parent link and its scope's effective readers change. Its descendants' rows do not change. Moves must also take locks in the same global order as policy changes (ancestor path root-to-leaf, then `scope_id`). A move between two subtrees is the most likely source of deadlocks under "top-down" locking.

### 3. Property tests against a naive evaluator

Write a deliberately slow reference evaluator that walks the container chain and applies the reader-list rule directly, with no `scope_access`. Then generate random trees, narrowings, widenings, moves, lazy scope creations and (later) group edits, and assert that `scope_access` equals the naive result for every (Item, principal) pair. Add a concurrent variant that runs two policy changes and a move under SERIALIZABLE or the chosen lock protocol, then asserts no extra reader. This is the cheapest guard against the specific risk of precomputation: a recompute bug that silently widens access. No public postmortem of a single-database precomputed ACL table drifting was found, so this rests on inference plus the Figma and OpenAI precedents. OpenAI added "redundant checks to ensure the data returned by our Redis cache matches the requesting user" after its 2023 cross-user leak ([OpenAI](https://openai.com/index/march-20-chatgpt-outage)).

### 4. Per-item sharing is a grant, never a new scope

When the kernel adds sharing, sharing an Item must **not** flip a scope node or create one. Model it as an additive row, `item_grant(item_id, principal, permission, granted_by, expires_at)`, so effective readers are `scope_access(scope_of(item)) ∪ item_grant(item)`. Inheritance stays intact: later changes to the container still flow to the shared Item, scope count stays tied to deliberate narrowing, and there is nothing to "restore". This avoids SharePoint's sprawl, where two files shared in one folder cost three scopes and nothing is ever cleaned up ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/manage-permission-scope)). Linear's per-issue sharing is shaped this way: recipients see the issue but not its team, project or cycle, and cannot reshare ([Linear](https://linear.app/docs/private-teams)). Search adds `OR item_id IN (granted items for principal)`, a small per-user set. A grant on a container flows to its descendants as a scope-level additive grant, but it still does not break inheritance. This revises the earlier plan of giving a shared Item its own `scope_id`, which would reproduce SharePoint's failure. For Step A, add the invariant that only an explicit narrowing can create a closed scope.

### 5. Parent readers do not learn that a narrowed child exists, by default

Products split here. Drive shows a limited-access folder to inherited users, who "can see the restricted folder in Drive but can't open it" ([Google](https://developers.google.com/drive/api/guides/limited-expansive-access)). Dropbox shows a "partially restricted" parent ([dropbox.tech](https://dropbox.tech/developers/implementing-restricted-access-with-nested-permissions-and-folders)). Teams owners see a private channel's existence but not its content ([Microsoft Learn](https://learn.microsoft.com/microsoftteams/private-channels)). Linear offers both: "Restricted" sub-teams are visible and joinable, "Private" ones are invisible ([Linear](https://linear.app/docs/private-teams)). The kernel already says hidden means ErrNotFound, so the consistent default is **invisible**. A narrowed child does not appear in its parent's child lists, child counts, activity feed or search facets for non-readers. An optional per-scope `discoverable` flag can later show a stub with an access-request action, as Linear's Restricted mode does. The stub reveals only that a restricted item exists, not its title, unless the owner opts in. Decide this in Step A, because child counts and list endpoints get built now. ErrForbidden from a transition's `allowed` list must be returned only after the visibility check passes, otherwise the Forbidden/NotFound split becomes an existence oracle.

### 6. Groups are principals, with a Leopard-style flattened membership table

In Step A, make `scope_access.principal` (and the future `item_grant.principal`) a typed principal ID that can hold users, groups and agents, so groups need no schema change. When groups ship, keep `group_member(user, group)` for direct membership and `group_closure(ancestor, descendant)` for nesting: the analogues of MEMBER2GROUP and GROUP2GROUP ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). Maintain both in the same transaction as membership edits, so removing a user from a group is one row and takes effect immediately. A request resolves its principal set once (user plus all ancestor groups) and joins `scope_access.principal = ANY(set)`. Reject cycles at write time with a reachability check under lock, and cap nesting depth. GitHub's nested teams are a tree with one parent per child, and secret teams cannot nest ([GitHub Docs](https://docs.github.com/en/organizations/organizing-members-into-teams/about-teams)). A tree with a depth cap of about 5 keeps closure maintenance bounded. Never expand groups into `scope_access`.

### 7. Bound `scope_access` growth before the first large narrowing

Measure in Step A how many rows one root narrowing writes on a realistic project (for example 100k Items, of which 30–60% are containers). If the number is large, add one level of indirection: each scope node stores `policy_scope_id`, the nearest narrowed ancestor-or-self, and `scope_access` rows exist only for narrowed scopes. Narrowing then writes one pointer per descendant scope node plus the reader rows of one scope, instead of readers × descendants. Search pays one extra join (`items → scopes → scope_access`) on small, hot tables. Nested narrowing (a narrowed child under a narrowed parent, effective = child list ∩ parent readers) still recomputes, but only over narrowed descendants, which product limits keep small. Jira's 50-levels-per-space cap is a reasonable starting bound. If the pointer approach is rejected, set a synchronous size cap the way SharePoint does at 100,000 items. Above it, revocations stay synchronous and grants may lag, never the reverse. This is the one recommendation that changes the Step A schema, so the measurement should come first.

### 8. Agent write-side rules

The narrow-only tree makes audience comparison cheap. A write is *not wider* than everything the agent read in a session if the destination's policy scope is equal to or below each source's policy scope and no grant widens it. Otherwise, compare the actual reader sets. Build that `audience_leq(dest, sources)` primitive in Step A and record each agent session's read set. Then enforce four rules. First, a write, comment, notification, webhook or external call whose audience is wider than the session's read set needs approval. That includes moves and new grants, which are audience changes. Second, rights are rechecked per tool call, not per session, as OWASP advises for long-lived tokens ([OWASP](https://owasp.org/Top10/A01_2021-Broken_Access_Control/)). Third, rendered outbound URLs and images built from model output are disallowed or allowlisted, since that was the Slack exfiltration channel. Fourth, content from externally writable fields is tagged as untrusted, and sessions that read it cannot take egress actions autonomously. Optionally, an agent session can be confined to one container subtree, the kernel analogue of Invariant's one-repository-per-session rule. The audience-widening approval already in the design is the right control, and these rules make it complete.

### 9. Read-time recheck when the index is asynchronous

When search moves to an external index or Watch feeds caches, keep the index filter as a coarse pre-filter and run every returned page through `visible()` against Postgres before returning it. Also check that the Item still exists and that its scope matches the indexed one. Over-fetch, and loop when the page comes back short. This is OpenFGA's prescribed pattern ([OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)) and GitHub code search's post-merge filter ([GitHub](https://github.blog/engineering/architecture-optimization/the-technology-behind-githubs-new-code-search/)). It costs one `WHERE id = ANY($ids)` join per page. Generate snippets and highlights only after the recheck. When the index watermark falls far behind, fail closed and show results from Postgres only, as Rovo hides a connector's results when its permission sync is stale ([Atlassian](https://support.atlassian.com/organization-administration/docs/how-connector-permissions-are-kept-in-sync/)). Prioritize scope and membership events over content events in the sequencer. Put `scope_id` on index documents, never reader lists, so membership changes write nothing to the index.

### 10. A replica LSN check as the zookie

Step A should route every permission-bearing read to the primary. When replicas arrive, each write returns its commit LSN alongside `min_seq`. A replica serves a request only if `pg_last_wal_replay_lsn()` has passed the caller's token, and otherwise falls back to the primary. This is the same revision-or-fallback logic SpiceDB uses on Postgres replicas ([SpiceDB](https://authzed.com/docs/spicedb/concepts/datastores)) and a single-database form of Zanzibar's "at least as fresh" zookie ([Zanzibar paper](https://www.usenix.org/system/files/atc19-pang.pdf)). Revocation needs care. A token proves that the reader's *own* writes are visible, not that another user's revoke is. Item reads that could expose content added after a revoke should either use the primary or carry the Item's latest policy LSN, which is Zanzibar's exact pattern of storing the zookie with the content.

### 11. Drift reconciliation job

Build the diff function in Step A, the same naive evaluator as #3 run against production rows, and schedule it later. It samples scopes continuously, recomputes their effective readers, and diffs them against `scope_access` and the group closure. Any *extra* row pages someone, because it is a leak. Missing rows are tracked as an availability problem. Add database invariants: every Item's container scope exists once it has children; a narrowed node belongs to exactly one container; there are no orphan `scope_access` rows; and a missing row means deny. The external-store version of this, run by Google and Canva, found "tens to hundreds of discrepancies per day" ([AuthZed / Canva](https://authzed.com/blog/the-dual-write-problem-in-spicedb-a-deep-dive-from-google-and-canva-experience)). The same-transaction design should find far fewer, and the job exists to prove that.

## Conclusion

The research changes where the kernel's risk lies. The scope table is the most defensible part of the design. It is a transactional version of what AuthZed sells as its top-tier product and of what Notion had to build offline. The question is no longer "precompute or not" but "how many things can reach Item data without passing through that table." Every serious incident found was a path that skipped or outran the authoritative check: a system note, an email, an aggregate, a lagging index, or an agent writing to a wider room. In other words, the kernel should treat egress paths as its main security boundary, with the scope table as one input to it.

The single-container, narrow-only tree also turns out to be useful beyond search. Because audiences nest, "is this write wider than what was read?" usually reduces to an ancestor test. That makes moves, sharing and agent writes cheap to check with one primitive, and few products have it. Keep that property: sharing as additive grants preserves it, while sharing that creates scopes would erode it the way it eroded SharePoint. The order of work follows from that. Lock in the invariants and function signatures in Step A, while there are few output paths and no data to migrate, and add the replica, index and group machinery when those consumers arrive.
