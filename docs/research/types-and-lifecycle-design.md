# Keep Types as data, code by name

A Type should be one strict, versioned data document with five parts. The first is a field schema with stable field IDs. The second is a small state graph where every state must declare a fixed semantic category. The third is a set of separate SLA and approval objects, plus optional case-style stages that hold task lists. The fourth is pure expressions for guards and conditions. The fifth is references by name to typed, versioned code units for every side effect. Every mature system surveyed converges on some version of this shape. Linear's fixed categories, Jira's catalog of named conditions, ServiceNow's and Pega's standalone SLA definitions, Salesforce's stages that contain steps, and XState's named guards all point the same way. Every system also ends up with an escape hatch into code, so the design question is where that hatch sits, not whether to have one. On change management the industry has settled the default. In-flight work stays pinned to the version it started on, and moving it to a new version is always explicit, narrow and mapped by a human. No engine re-interprets running instances automatically. The kernel can do better than Jira, which mutates every issue at once and silently skips its rules. To do that it should treat migration as a data operation (a state map plus field upcasters) applied at safe boundaries. It should also pin only lifecycle behavior. Schema should evolve by upcasting and policy should always apply at the latest version. The strongest objections hold up in part. Interpreter replay across versions, Temporal's 51,200-event history cap, field sprawl and rigid state machines for case work are all real risks. Each is manageable if the kernel stays narrow: chat traffic never enters workflow history, lifecycles stay thin guardrails rather than agent plans, and each product surface ships opinionated default Types. Much of this rests on vendor documentation and forum threads rather than measured outcomes, so the upcoming spike has to produce the evidence that this research could not.

## Prior art converges on categories, named rules and standalone SLAs

The work trackers and the orchestration engines solve different halves of the problem, and the kernel needs both halves. **Trackers model a lifecycle as a flat state machine with rules attached to transitions.** A Jira transition bundles "triggers, conditions, validators, post functions and properties". Jira Cloud ships 17 built-in conditions and 10 optional post functions, and certain "essential" post functions cannot be deleted or reordered ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/configure-advanced-issue-workflows/)). Linear goes to the other extreme. It has no transitions or guards at all, only a fixed, ordered set of categories (Backlog, Unstarted, Started, Completed, Canceled, plus Triage). Teams may rename and add statuses "as long as each category keeps at least one status" ([Linear](https://linear.app/docs/issue-property)). YouTrack makes lifecycle rules into JavaScript modules. Each rule declares the fields it `requires`, and it "cannot be enabled" if they are missing ([YouTrack](https://www.jetbrains.com/help/youtrack/devportal/on-schedule-rules.html.md)). **Orchestration DSLs model a lifecycle as a task graph over a JSON or YAML document, with an expression language for data.** Amazon States Language uses JSONPath predicates in `Choice` states ([AWS](https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-human-approval.md)). Serverless Workflow 1.0 uses jq inside `${ }` and lists A2A and MCP as first-class call protocols ([Serverless Workflow](https://www.mintlify.com/serverlessworkflow/specification/concepts)). XState keeps guards and actions as named implementations supplied through `setup()`, and it persists only a snapshot of the running machine ([Stately](https://stately.ai/docs/xstate/v6/cheatsheet)).

The table below picks out the one lesson worth taking from each system.

| System | Lifecycle shape | Lesson to copy | Lesson to avoid |
|---|---|---|---|
| Jira | Arbitrary graph; transitions carry conditions, validators, post functions | Catalog of named, parameterized rules; validators check transition-screen input | A closed catalog pushes logic into marketplace apps and ScriptRunner Groovy |
| Linear | Fixed ordered categories; no transitions | A mandatory category on every state lets boards, reports and SLAs work across teams | No guards or approvals, so it is too thin for helpdesk or case work |
| YouTrack | JS rule modules (guard + action); cron-based timers | Rules declare the fields they need, checked when the rule is enabled | No timer per item; time behavior comes from cron searches |
| Step Functions | JSON task graph; `waitForTaskToken` | Approval = a waiting task completed by an external token; immutable versions plus weighted aliases | A short JSON definition still needs Lambdas, API Gateway and SNS around it |
| Serverless Workflow | 12 task types; jq expressions; per-task timeouts | Side-effect-free expression language; A2A and MCP as call protocols | `run` executes arbitrary containers and scripts, so the escape hatch is wide open |
| XState | Statechart: nesting, parallel regions, history | Named guards, actions and delays referenced by name; snapshot persistence | History and deep nesting are too hard for work-item authors |
| CMMN | Stages, sentries, discretionary tasks, milestones | "Available vs active" tasks; sentries; milestones | The notation hid its logic in rules, and the standard failed in the market |
| Salesforce Orchestrator | Sequential stages, one active, each with parallel or sequential steps | Interactive steps create work items for a person; background steps run automatically | Classic approvals were replaced by Flow approvals that lacked recall and approval history at launch |
| Pega | Case → Stage → Process → Step; SLAs at every level | Goal, deadline and a repeating passed deadline, with urgency and reassignment | Five manual patterns for in-flight changes, none of them clean |
| ServiceNow | SLA definitions with start, pause, resume, stop, reset and cancel conditions | SLA as its own object, attached to an item by conditions | Overlapping conditions silently break SLAs, and the vendor's own docs warn about it |
| Dataverse | More than 15 places where logic can live | Server-side (table-scoped) rules apply to every caller | Logic sprawls across tiers that overlap |

Three patterns stand out. First, **a semantic category layer is what lets anything work across Types.** Linear enforces it, and it is the reason boards, cross-team reports, SLAs and agents can reason about "is this done?" without understanding each Type's graph. Second, **"rules as data" works when the data names code rather than embedding it.** Jira's catalog, XState's `setup({ guards, actions })` and YouTrack's `requirements` all keep definitions serializable while the real logic lives in versioned code. That maps directly onto Temporal activities as the catalog. Third, **SLAs are almost never lifecycle states.** ServiceNow attaches an SLA when its start condition matches and neither stop nor cancel matches. It then pauses, resumes, re-attaches on reset, and cancels by a fixed evaluation order. Its docs warn that if start is a subset of stop the SLA never attaches, and if pause is a subset of start it "gets stuck in a paused state and is then canceled" ([ServiceNow](https://www.servicenow.com/docs/r/it-service-management/service-level-management/c_SLAConditions.html)). Pega measures goal and deadline from the start of the case, stage, process or step. Its passed deadline repeats up to a limit, each interval raises a 0–100 urgency score, and escalation can reassign the work or resolve the case ([Pega Academy](https://academy.pega.com/node/80721)). Linear's SLA rules use first-match ordering and **do not apply retroactively** ([Linear](https://linear.app/docs/issue-property)). That choice previews the versioning question covered below.

Where rules are enforced matters as much as how they are written. Dataverse business rules scoped to a form are "only enforced in the app in which the logic is implemented". Rules scoped to the table run on the server "when any app, flow, or API is used" ([Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/power-platform-architecture/5-logic)). For a kernel where AI agents act through APIs and never see a form, that settles the question. **Every invariant belongs in the schema and the transition validators on the server. Forms hold presentation only.**

## Case work needs a backbone with task lists, not statecharts or CMMN

The tracker, helpdesk and cross-team case surfaces need different amounts of flexibility, and the evidence warns against both extremes. Van der Aalst and colleagues argued two decades ago that in classic workflow "routing is the only mechanism driving the case". It focuses "on what should be done instead of what can be done", and workers who bypass it turn the system into "more a liability than an asset" ([van der Aalst et al.](https://www.vdaalst.com/publications/p252.pdf)). The standard built to fix this, CMMN, failed. Camunda found that "even the most complex case management processes still had quite a lot of predictable parts", so teams had to learn BPMN as well. CMMN's logic was hidden, so "the only way to know how a sentry would trigger" was a text annotation. After Camunda shipped a CMMN engine and modeler, the expected uptick in adoption "never happened, sadly", and the founders dropped CMMN from their book in 2019 ([Camunda](https://camunda.com/blog/2020/08/how-cmmn-never-lived-up-to-its-potential/)). An academic comparison found that CMMN's ease-of-use scores were the least reliable of the languages studied. It found that modeling resources through entry criteria "can make the model very complex", and that both CMMN and its rival DCR are "mostly unknown for practitioners" ([arXiv 2103.11218](https://arxiv.org/pdf/2103.11218)). The same Camunda post offers a useful counterpoint. DMN decision tables were adopted "much faster and more enthusiastically". **Declarative formats succeed for narrow, tabular, side-effect-free concerns and struggle with control flow over time.**

The workable middle ground is the one the commercial platforms ship. In Salesforce Orchestrator, "only one stage in an orchestration can be in progress at a time". Steps inside a stage run in sequence or in parallel, interactive steps create work items in a Work Guide, and evaluation flows decide entry and completion ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/orchestrator-basics/get-to-know-orchestrator)). Pega layers Case, Stage, Process and Step in the same way. The recommendation that follows is a **visible status or stage backbone, plus per-stage task lists whose items can be human, agent or system work**. Each task can be required, optional or discretionary ("available"), and stages enter and exit through sentry-style conditions (an event plus an expression). Milestones are named conditions that report progress. This captures "three reviews in parallel, any order, optional fourth" without exposing statechart history, deep nesting or CMMN's full lifecycle. No work tracker surveyed exposes those to its users.

For AI agents, Anthropic's distinction applies. Workflows are "predefined code paths" that offer "predictability and consistency", while agents "dynamically direct their own processes" ([Anthropic](https://www.anthropic.com/research/building-effective-agents)). **The lifecycle should be the agent's guardrail, not its plan.** The guardrail covers which states exist, which transitions are allowed, which fields are required and which approvals block. What an agent does inside a state or task is emergent and should not be modeled. If the lifecycle encodes the agent's plan, it duplicates the agent and goes stale. Agents fit most naturally where a model has explicit tasks with assignees, such as Step Functions task tokens or Salesforce work items. An agent is then just one kind of assignee completing the same token a human would. This is an inference: no study of state machines constraining agents in production work tools turned up.

Chat is the boundary case. A Slack-like message has essentially no lifecycle. Modeling every message as an Item that runs a workflow would be overhead with no benefit, and the Temporal limits below rule it out anyway. The kernel should allow Types with **no lifecycle at all**. Such Types share identity, fields, permissions, links and search, but never start a workflow.

## Every engine pins by default; the upgrade path is the real design problem

The evidence is unanimous on the default. Camunda says "Existing instances are not affected by a new deployment unless they are migrated" ([Camunda 7](https://docs.camunda.org/manual/7.9/user-guide/process-engine/process-instance-migration)). Orkes says "Changes to a definition never affect executions that are already running" ([Orkes](https://orkes.io/content/developer-guides/versioning-workflows)). A Step Functions execution binds to the version or alias it started with ([AWS](https://docs.aws.amazon.com/step-functions/latest/dg/execution-alias-version-associate.html)). ServiceNow Flow Designer reportedly does the same, but only a community answer confirms it ([ServiceNow Community](https://www.servicenow.com/community/developer-forum/flow-designer-what-happens-to-ritms-after-flow-updates/m-p/3455658)). Upgrades differ widely, as the table shows.

| Mechanism | Who uses it | How it works | Cost |
|---|---|---|---|
| Declarative state mapping | Camunda 7 and 8 | Map every active source element to a target element of the same type; validate the plan, then validate each instance | Strict limits: wait states only, no incidents; jobs and expressions are **not re-evaluated**; the engine "doesn't detect" unsafe mappings |
| Code branching | Temporal patches, Pega circumstancing | Old and new paths coexist in code, chosen per instance | "Patches accumulate into real code complexity"; circumstanced rules can linger forever |
| Checkpoint and restart | Temporal Upgrade on Continue-as-New, Orkes terminate/restart | Move to the new version at a safe boundary | Restarting can repeat side effects unless steps are idempotent |
| Mutate in place | Jira | Admin maps deleted statuses; every issue moves on save | "Workflow rules won't be triggered"; no pinning, preview or easy undo |
| Keep old shapes and drain | Pega, Temporal Draining/Drained | Old states stay reachable only for old instances until a report shows none remain | Clutter in the definition; needs drain reporting |

Sources: [Camunda 8.4](https://unsupported.docs.camunda.io/8.4/docs/components/concepts/process-instance-migration/), [Temporal blog](https://temporal.io/blog/ga-worker-versioning-public-preview-upgrade-on-continue-as-new), [Pega Academy](https://academy.pega.com/topic/managing-flow-changes-cases-flight/v1), [Orkes](https://orkes.io/content/developer-guides/versioning-workflows), [Atlassian](https://support.atlassian.com/jira-software-cloud/docs/move-issues-to-new-statuses-while-updating-your-workflow/).

Temporal's own tooling matured during 2026. **Worker Versioning reached GA on March 30, 2026, and Upgrade on Continue-as-New is in Public Preview.** Temporal calls the latter "the cleanest path to zero-patch deployments" ([Temporal blog](https://temporal.io/blog/ga-worker-versioning-public-preview-upgrade-on-continue-as-new)). PINNED workflows complete on a single worker deployment version. Ramping sends a 0–100% share of new workflows to a new version, bucketed by workflow ID. A version that still has open pinned workflows shows as "Draining" until they close ([Temporal docs](https://docs.temporal.io/worker-versioning)). This matches the kernel's design closely. The lifecycle state and fields of an Item live in Item data, the interpreter is generic, and so **migrating a Type version is a data operation rather than a code-replay problem**. The data operation is to map old state to new state, upcast fields, and apply the result at a continue-as-new or signal boundary.

Pinning is not isolation, and this is the trap that matters most. Camunda notes that when a pinned definition's code reference stays the same, in-flight instances pick up the new code anyway ([Camunda versioning](https://docs.camunda.io/docs/components/best-practices/operations/versioning-process-definitions/)). The same is true of any named activity a pinned Type calls. Temporal's forum makes a related point: changing an activity's code does not break determinism, but changing its semantics silently affects in-flight work ([Temporal forum](https://community.temporal.io/t/versioning-patching-when-using-dsl/5031)). **Named code units therefore need their own semantic versions, and a Type version must pin to a major version of each one.**

Pinning also cuts the wrong way for some parts of a Type. Security and compliance policy usually has to apply to old Items immediately, and pinning the field schema breaks cross-Item queries once fields are renamed or retyped. Camunda warns that history after migration "can be confusing", recommends splitting processes that run longer than about six months at idle points, and says migration takes "many migration iterations" against production-like data ([Camunda versioning](https://docs.camunda.io/docs/components/best-practices/operations/versioning-process-definitions/)). Salesforce caps each flow at **50 versions**, and admins report deleting old versions mid-deployment, which "can feel risky" ([Trailblazer Community](https://trailhead.salesforce.com/trailblazer-community/feed/0D54V00007GJCSvSAP)). The design conclusion is to **pin the lifecycle, evolve the schema and float the policy**:

| Part of a Type | Version behavior | Why |
|---|---|---|
| Lifecycle (states, transitions, stages, SLAs, approvals) | Pinned per Item; upgraded only by explicit migration | In-flight timers, approvals and stage progress must not shift under people |
| Field schema | Stable field IDs; read-time upcaster chain vN→vN+1; optional backfill | Cross-version reporting and search need one field identity |
| Policy (permissions, retention, data classification) | Always evaluated at the latest version | Compliance cannot wait for old Items to drain |
| Forms | Always latest, rendered against the upcast schema | Presentation has no in-flight state |
| Named code units | Semantic versions; the Type pins major versions | Pinning means nothing if referenced code changes meaning |

For field evolution, the event-sourcing community's patterns carry over directly. These are tolerant mapping with defaults, upcasting as "a middleware between the deserialisation and application logic", versioned type names, and copy-transform to a new store, all under the stance "you should not change the past" ([event-driven.io](https://event-driven.io/en/simple_events_versioning_patterns/)). Fowler's parallel change (expand, migrate, contract) covers write-time changes. He warns that the risk is never reaching the contract step ([Martin Fowler](https://martinfowler.com/bliki/ParallelChange.html)). With stable field IDs, most renames become changes to metadata only. Removing a field should be a contract step that stays blocked while any pinned Item, saved report or integration still references it. One gap remains open. No sourced material covers values that cannot be converted during a retype. Quarantining them in a side field is a reasonable guess, but it is untested.

## Jira migration should import data faithfully and logic skeptically

Importers move the core data reliably. YouTrack moves issues, comments, attachments, links, work logs, watchers and history. Its continuous import polls "every two minutes", but works only for Jira Server, because continuous import from Cloud "can lead to inconsistent synchronization of user data". Jira Cloud also requires a CSV export of users ([JetBrains](https://www.jetbrains.com/help/youtrack/cloud/new-import-from-jira.html.md)). Even Atlassian's own Server-to-Cloud tool does not migrate "any custom fields from apps", global permissions, or custom notifications and events ([Atlassian](https://support.atlassian.com/migration/docs/what-gets-migrated-with-the-jira-cloud-migration-assistant/)). Logic is worse still. ScriptRunner says its Server scripts "will not work automatically on Jira cloud" and need reworking, and it sells an hourly service to do that rewriting ([ScriptRunner](https://www.scriptrunnerhq.com/inspiration/blog/rewriting-scriptrunner-scripts-for-migration)).

Linear's experience shows that faithful porting is the wrong goal. Its enterprise switch stories are vendor-reported. Opendoor moved 500 seats in two weeks with a clean-slate setup, Oscar moved 600+ people in about a month, and **"None of the featured enterprises migrated their full backlog."** Linear's playbook lowers risk with two-way Jira sync during phased pilots, a read-only Jira archive for history, and help with Jira contracts ([Linear](https://linear.app/switch)). The barriers are organizational. Leadership reporting is the one cited most often, followed by the depth of the integration ecosystem, cost, and doubts about enterprise features. One team could not prove that "velocity feels better" without its Jira reports ([JTBD UX](https://jtbdux-protocol.pages.dev/discovery-and-research/choosing-to-switch/jira-is-the-most-hated-tool-in-engineering-so-why-does-it-take-years-to-leave), a secondary source).

The kernel's migration story follows from this. **Map each Jira (project, issue type) to a candidate Type, but deduplicate before you create anything.** Shared workflow schemes collapse into shared Types. Jira statuses become states, and each one needs a category assigned (Jira has status categories, but their exact mapping was not verified here). Custom fields become fields with stable IDs, and unused ones are flagged rather than imported. Conditions, validators and post-functions go into a "needs review" report, with suggested equivalents from the kernel's catalog. Automatic translation is not attempted. History becomes Item events, so timelines stay credible, and the original Jira key is kept as an alias. Identity mapping is planned up front. The rollout runs in four phases: a one-time bulk import, incremental sync while teams pilot, cutover, then a read-only archive. The default offer should be **clean-slate Types from opinionated templates plus selective import**, because a 1:1 port imports sprawl. Executive and portfolio reporting has to work on day one. That is where switches stall, and it depends on the category layer and stable field IDs described above.

## Authoring works when text is canonical, the diagram is a view and AI explains first

Two separate editors cause drift, and every hybrid surveyed shows it. Step Functions' Workflow Studio pairs a canvas, per-state forms and a Definition view. Console edits still had to be copied back into SAM templates by hand ([AWS Compute Blog](https://aws.amazon.com/blogs/compute/prototyping-at-speed-with-aws-step-functions-new-workflow-studio)). IaC export arrived only in November 2024 ([AWS](https://aws.amazon.com//about-aws/whats-new/2024/11/infrastructure-code-template-generation-aws-step-functions)). ServiceNow developers warn that mixing update sets with Git breaks deployments, so "every developer on an instance should follow the same workflow" ([ServiceNow Community](https://www.servicenow.com/community/servicenow-ide-sdk-and-fluent/relevance-of-update-sets-when-using-ide-or-sdk-with-git/m-p/3332962)). Stately listed bidirectional editing and GitHub sync as "coming next", not shipped ([Stately](https://prod.stately.ai/blog/2023-11-20-stately-studio-2-0)). Demand for config-as-code is real but unmet in work management. Atlassian has long-standing tickets requesting an official Terraform provider for Jira ([JRACLOUD-92940](https://jira.atlassian.com/browse/JRACLOUD-92940)), and a paid Marketplace app sells Terraform-based configuration with Git versioning ([PlanApply](https://marketplace.atlassian.com/apps/1235202/planapply-for-jira-cloud-configuration-management)). Power users want tabular and textual views as well. Jira users asked for bulk edits and import and export of workflows as state/transition tables ([Atlassian Community](https://community.atlassian.com/forums/Jira-articles/Announcing-the-Workflow-Builder-Agent-Beta-in-the-New-Jira/ba-p/3084198)). They also protested when a redesigned editor lost the ability to reuse one transition across statuses ([Atlassian Community](https://community.atlassian.com/forums/Jira-questions/Jira-Cloud-UI-Recent-Regressions-Admin-Feedback/qaq-p/3128875)).

The design answer is a **single canonical text document per Type version**. The diagram, the table and the form editor are all projections of it. Each Type also needs a declared source of truth. A Git-managed Type accepts UI edits only as generated pull requests. A UI-managed Type exports to Git and accepts Git changes only as proposals. Edits never write directly through the other path.

AI authoring has shipped everywhere, and practitioners report the same result across vendors. Atlassian's Workflow Builder Agent drew comments that it could not see the workflow being edited and gave generic answers. Others valued it for documentation and visibility into rules ([Atlassian Community](https://community.atlassian.com/forums/Jira-articles/Announcing-the-Workflow-Builder-Agent-Beta-in-the-New-Jira/ba-p/3084198)). One practitioner judged Salesforce's Agentforce for Flow "good at 70% of the job and mediocre at the last 30%", weak on nested branching and legacy fields, and only able to stub external callouts. Its AI summaries of a contractor's flow were more accurate than the contractor's own description ([dev.to](https://dev.to/dipojjal/agentforce-for-flow-what-admins-need-to-know-in-2026-hdh), a single practitioner source). Camunda's BPMN Copilot officially modifies only diagrams it created, and its changes "may affect unrelated parts of the diagram" ([Camunda](https://docs.camunda.io/docs/components/early-access/alpha/bpmn-copilot/)). ServiceNow pins exact tables with hashtags so that generated flows reference the right data ([ServiceNow](https://www.servicenow.com/community/developer-advocate-blog/unleashing-the-power-of-now-assist-for-flow-generation-a-game/ba-p/3116438)). **Explaining an existing configuration works today, while editing customized configuration is unreliable.** Grounding the model on the real definition is the difference between the two. The kernel should therefore lead with AI that explains: it summarizes a Type, draws its diagram, explains why a transition is blocked, and explains what a draft changes and how many in-flight Items it affects. Generation comes second, always produces a draft and a diff, and never activates anything. No vendor published acceptance or accuracy rates, so the reliability of AI edits is still unmeasured.

Governance has to be designed in from the start. Sprawl forced Atlassian to retrofit hard limits. Since March 2026 Jira enforces **700 fields and 150 work types per space**, and from September 2026 it adds limits that include **150 workflows per scheme and 200 statuses per workflow** ([Atlassian](https://support.atlassian.com/jira-cloud-administration/docs/data-limits-and-guardrails/)). Admins have removed "tens of millions of unused fields and work types" with new bulk cleanup tools ([Atlassian blog](https://www.atlassian.com/blog/how-we-build/optimisation-tools-for-jira)). Atlassian's own tests found that "the number of custom fields had the greatest effect on average response times" ([Atlassian](https://confluence.atlassian.com/enterprise/managing-custom-fields-in-jira-effectively-945523781.html)). Notion documents a 500-property limit and slowdowns from chained formulas and rollups ([Notion](https://www.notion.com/help/optimize-database-load-times-and-performance)). Jira's two project models show the ownership trade-off. Team-managed spaces are fast but cannot be made consistent across spaces. In company-managed spaces, any scheme change affects "every company-managed space that uses that configuration" ([Atlassian](https://support.atlassian.com/jira-software-cloud/docs/what-are-team-managed-and-company-managed-projects/)). The kernel therefore needs three authoring roles. Type owners manage shared Types. Team creators manage local forks, which record what they were derived from and can be promoted into shared Types. End users change data only. It also needs a shared field library that is offered before anyone creates a new field, usage telemetry on every field and Type, caps from day one, and bulk retirement that can be rolled back. The evidence on citizen developers is mostly governance warnings, not success rates. Practitioners say business staff were "never offered a practical governance model" ([The Register forum](https://forums.theregister.com/forum/all/2023/11/08/gartner_shadow_it_low_code/)).

## The strongest objections survive in narrowed form

The adversarial case is serious. Most objections do not kill the design. Each one rules out a specific way of building it.

| Objection | Strongest evidence | What survives | Design consequence |
|---|---|---|---|
| Inner-platform effect: the Type format becomes a bad programming language | ScriptRunner Groovy filled Jira's gaps and must be rewritten for Cloud ([ScriptRunner](https://www.scriptrunnerhq.com/inspiration/blog/rewriting-scriptrunner-scripts-for-migration)); ASL kept adding intrinsic functions ([AWS](https://aws.amazon.com/blogs/aws/aws-step-functions-adds-updates-to-choice-state-global-access-to-context-object-dynamic-timeouts-result-selection-and-intrinsic-functions-to-amazon-states-languages)); Vercel argues "the best workflow engine is a programming language" ([Vercel](https://vercel.com/blog/the-best-workflow-engine-is-a-programming-language), vendor-biased) | Valid for control flow. It does not apply to schemas, categories, decision-table-style guards or SLA conditions, where DMN-style declarative formats succeed | No loops, variables or retries in Type data. Side effects only through named, typed code. Control flow beyond stages and tasks becomes a named child workflow written in code |
| The interpreter must replay every Type version forever | Temporal staff: the parser must "handle both old and new dsl structure"; "you have to define yourself the semantics of updating the DSL" ([Temporal forum](https://community.temporal.io/t/versioning-patching-when-using-dsl/5031)) | Valid. Two version axes stack: Type version × interpreter version | Keep the Temporal workflow thin, as a scheduler for durable effects only. Pin interpreter releases with Worker Versioning. Run a replay corpus of real histories per live Type version in CI |
| History limits break long-lived Items | Hard cap of 51,200 events or 50 MB; warnings at 10,240 events or 10 MB; 2,000 pending signals or activities ([Temporal](https://docs.temporal.io/workflow-execution/limits)) | Fatal for "chat channel as a workflow", manageable for cases | Messages and comments never become signals. Continue-as-new at stage boundaries or event thresholds, carrying the Type version explicitly. Audit lives in the Item event log, not in Temporal history |
| Lazy start creates two code paths | Inference from the design: transitions before the workflow starts run outside Temporal, transitions after run inside | Valid unless semantics live in one place | One pure transition function (definition + state + event → new state + effects) used on both paths. Starting the workflow is idempotent, keyed by Item ID, with a version check on the Item row |
| Pinning causes stuck instances, version explosion and confusing reports | Camunda's migration effort and six-month split advice; Salesforce's 50-version cap ([Camunda](https://docs.camunda.io/docs/components/best-practices/operations/versioning-process-definitions/); [Trailblazer](https://trailhead.salesforce.com/trailblazer-community/feed/0D54V00007GJCSvSAP)) | Valid for bundles that pin everything | Pin the lifecycle only. Upcast the schema, float the policy. Show drain dashboards, cap live versions, and force migration or a waiver at the cap |
| Rigid lifecycles fail knowledge work | Van der Aalst on routing-driven rigidity ([paper](https://www.vdaalst.com/publications/p252.pdf)) | Valid, but CMMN's failure shows full flexibility fails too | Predictable backbone plus discretionary tasks. Global transitions to "waiting" or "canceled". Lifecycle as an agent guardrail, not a plan |
| One kernel for everything becomes Lotus Notes or Wave | Notes landed "a development tool on each and every desktop" ([Buttondown](https://buttondown.com/blog/lotus-notes-email)); Wave was "too complicated" ([InfoWorld](https://www.infoworld.com/article/2625908/why-google-wave-failed--too-complicated--no-fun.html)) | The strongest objection, and it is about product, not architecture | Each surface (tracker, chat, helpdesk, cases) ships as an opinionated product on built-in Types. Configuring Types is an admin capability, not the front door |
| User-defined schemas are the performance problem | Jira response times grow with the number of custom fields; Notion's property and rollup limits | Valid. The hard part is indexing and search over arbitrary schemas, not the workflow engine | Fields compile to typed storage with generated indexes, not EAV. Shared field library and caps from day one |

The survivors share one theme. **The kernel is safe only if it stays narrow.** It owns identity, typed fields, state categories, guardrail transitions, SLAs, approvals and stages. It hands everything procedural to named code and everything conversational to plain Items without lifecycles. No public post-mortem of a large DSL-interpreter-on-Temporal system was found, in either direction. Community frameworks such as Zigflow show the pattern is being attempted but not that it has been proven at scale ([Temporal forum](https://community.temporal.io/t/a-new-dsl-workflow-framework-based-on-temporal/6431)).

## Concrete recommendations for format, release, authoring and the spike

### The Type format separates data from named code

| Element | Data in the Type | Named code (versioned, typed) |
|---|---|---|
| Fields | Stable ID, display name, type, options, default, invariants as expressions, computed fields (synchronous formula only) | Asynchronous rollups across Items; custom field types |
| States | ID, name, **required category**, entry and exit conditions | None |
| Transitions | From/to, guard expression, required fields, actor constraints (role, group, separation of duties), action references with parameters | Guards an expression cannot express, such as a lookup in an external system |
| Stages (optional) | Ordered list, one active; tasks with assignee kind (human, agent, system), required/optional/discretionary, entry and exit sentries, milestones | Child workflows for complex procedural work inside a task |
| SLAs and timers | Standalone objects: start, pause, resume, stop, reset and cancel conditions; goal, deadline and repeating passed deadline; business calendar; urgency increments; escalation action references | Notification and reassignment activities |
| Approvals | Waiting step: approver resolution rule, quorum (any/all/N), separation of duties, timeout tied to an SLA, recall allowed; completed by token (human or agent) | Resolvers for dynamic approver lists |
| Policy | Permissions, data classification, retention; always evaluated at latest | None |
| Hooks | Event subscriptions referencing named actions, with idempotency keys | The actions themselves |
| Declarations | Each code unit's `requires` (fields and types) checked when the Type is published, as in YouTrack | None |

For state categories, start from Linear's proven set (triage, backlog, todo, active, done, canceled) and add one **waiting** category. Helpdesk and case work need "blocked on customer or third party" as a semantic state, because SLAs pause on it. That addition is a judgment call, not sourced. For the expression language, use something typed, side-effect free and bounded in cost. CEL is the natural candidate. jq, as used in Serverless Workflow, is the alternative, but it is a data-transformation language rather than a predicate language. Publish-time validation should type-check every expression against the field schema. It should also flag ServiceNow-style SLA conflicts, such as start being a subset of stop or pause being a subset of start, before they reach production.

### The release process turns change into a staged rollout

| Step | What happens | Precedent |
|---|---|---|
| Draft | Editable version; AI explains the diff in plain language | Salesforce Flow Summarization |
| Validate | Schema type-check, expression type-check, `requires` satisfied, SLA conflict lint, state-map completeness, category changes flagged | Camunda plan validation; YouTrack requirements |
| Dry run | Replay the draft against a snapshot of real in-flight Items: counts per state, failing transforms, timers that would move, approvals affected | Pega: "always test the assignments with existing cases" |
| Approve | Required by policy when the blast radius is large (many open Items, shared Type, policy change) | Gap: no engine ships this natively |
| Publish | Immutable version; new Items use the current pointer | Step Functions versions and aliases |
| Ramp | Percentage or cohort (team, tenant) of new Items on the new version; metrics broken out by version | Step Functions weighted aliases; Temporal ramping |
| Migrate (opt-in) | State map plus field upcast, per Item in its own transaction, at a wait point or continue-as-new boundary; hooks **off** by default; an audit event per Item; pause and abort; reverse map kept where possible | Camunda batch migration; Temporal Upgrade on Continue-as-New |
| Drain | Dashboard of Items per old version; version cap; retire when empty | Temporal Draining/Drained; Pega drain reports |

Rollback is asymmetric. Moving the current pointer back is always safe for new Items. Migrated Items roll back only through a reverse map or the event history.

### The authoring model is one canonical document, two front doors

Every Type version is a canonical text document (YAML or JSON with a published schema). The visual editor, the state/transition table and the Git file are views of that document. Each Type declares whether Git or the UI is its source of truth. Edits through the other path become proposals. Business teams author in the UI from templates and the shared field library. Platform teams keep built-in Types and named code in Git, with CI running validation, dry runs and replay tests. AI works in explain mode by default and in draft mode on request, grounded on the actual Type, its dependencies and live Item counts. It never publishes.

### The kernel spike must answer the questions this research could not

| Test | Pass criterion |
|---|---|
| Interpreter replay across versions | Histories recorded under interpreter v1 for three Type versions replay cleanly on v2 in CI |
| Long-lived case | A helpdesk Item with hundreds of SLA pauses and resumes, approvals and reassignments over simulated months stays under the 10,240-event warning through continue-as-new, with the Type version carried forward |
| Chat-scale Items | Thousands of messages per channel with zero Temporal workflows; search and permissions still work |
| Lazy start race | Concurrent transitions during workflow start produce one consistent state and no duplicate effects |
| In-flight migration | 10,000 Items with pending timers and open approvals migrate by state map; timers are recomputed or preserved as declared; abort halfway leaves a consistent state |
| SLA semantics | ServiceNow's six-condition evaluation order passes a property-based test suite; the conflict linter catches the documented failure cases |
| Approval by agent | An AI agent completes an approval through the same token or update path as a human, under separation-of-duties rules, with an audit trail |
| Cross-version reporting | "Open items by category and severity" stays correct after a field rename and a retype across three versions |
| Jira import | One real, messy Jira project imports with history; the review report lists every condition, validator and post-function; the deduplicated Type count is measured |
| Authoring round trip | UI edit → generated PR → merge → publish, with no drift; the AI explanation of a draft diff is judged accurate by its author |
| Schema performance | Query latency on typed, indexed custom fields stays flat from 50 to 700 fields per Type |

## Conclusion

The research changes the design question. The risky choice is not data-driven Types versus code-driven workflows. Prior art shows the winning shape is data that names code. The risky choice is treating a Type as one indivisible pinned bundle and the interpreter as a general-purpose engine. Splitting version behavior (pin the lifecycle, upcast the schema, float the policy) and keeping the Temporal workflow as a thin scheduler for timers, waits and approvals turns the most serious objections into engineering problems with known precedents. Category-first states, standalone SLAs and token-completed approvals also make humans and agents interchangeable assignees, which no surveyed tracker does natively.

The evidence base is thinner than it looks. Most of it is vendor documentation, forum threads and single practitioner accounts. There are no failure rates for citizen-built workflows, no accuracy data for AI authoring, no post-mortems of interpreter-on-Temporal systems, and no studies of state machines constraining agents. The biggest remaining risk is the product risk from Lotus Notes and Wave, not an architectural one. If the tracker, helpdesk and chat surfaces do not each feel opinionated and complete before anyone opens the Type editor, the kernel's flexibility will read as a development tool handed to every desk. The spike should test that alongside the history limits.
